## Intent

**Problem:** Sculpted height and painted control-map data live only in Terrain3D's unsaved in-memory region storage. `TerrainPhase` regenerates a flat 256×256 region on every boot (`TerrainPhase.cs:44-77`), `ScenarioData.TerrainRef` is a dead field (only mixed into a hash, never read to load terrain), and neither the scenario JSON, the `.chimera.zip` package, nor the load path carries any terrain payload — so all terrain edits vanish on save/reload, on the F5 Edit→Play re-apply, and on export/import. Separately, terrain sculpt/paint strokes have no undo/redo (only entity placement does), and every stroke emits a red `Terrain3DEditor:_store_undo: _terrain isn't initialized` push_error.

**Approach:** On map save, persist the live Terrain3D region data (height + control + color, captured together by `data.save_directory`) into a folder beside the scenario, write that folder's `res://` path into `ScenarioData.TerrainRef`, and bundle the region files into the `.chimera.zip`. On load, when `TerrainRef` is non-empty, restore that data into the already-built Terrain3D node (assign `data_directory`) and trigger a nav rebake, instead of leaving it flat; keep the empty-`TerrainRef` flat fallback byte-identical for new/legacy maps. Add per-stroke snapshot-based terrain undo/redo pushed onto the **same** `EditorHistory` instance `EntityPlacer` uses (so terrain and entity ops interleave LIFO), and eliminate the `_store_undo` red line.

## Boundaries & Constraints

**Always:**
- Presentation-layer only, plus populating the existing pure-C# `ScenarioData.TerrainRef` string and adding a terrain entry to the `.chimera.zip` format. NO changes to `src/Core` sim tick systems, `src/Combat`, `src/Economy`, `src/Navigation` sim, or `SimChecksum`. `ScenarioData`/`ScenarioSerializer` stay pure C#/JSON — no new sim-state types, no new per-entity arrays.
- The empty-`TerrainRef` path (new map, legacy map, PlaneMesh fallback) stays behaviorally identical to today: flat region imported by `TerrainPhase`, no restore, no error, no new log noise.
- Terrain stroke undo/redo pushes onto the **single shared** `EditorHistory` that `EntityPlacer` already owns and drives via Ctrl+Z/Y — not a second parallel stack. Interleaved entity + terrain operations undo/redo in strict LIFO with no cross-corruption.
- Restored terrain must feed the NavMesh rebake (`NavObstacleManager.MarkDirty()`), and byte-identical saved region data must produce an identical bake across separate loads.
- `save_directory` serializes height + control + color together; the persistence path round-trips whatever the control map holds, independent of whether texture painting currently writes to it.
- Restore and packaging must never leave the game in a crashed/hung state on a missing or corrupt terrain reference — fall back to flat and log.

**Block If:**
- Per-region height+control snapshot for undo cannot be read from C# via any public `Terrain3DData`/`Terrain3DRegion` method AND the `save_directory`-snapshot fallback (Design Notes) is also unworkable — i.e. there is genuinely no way to capture a restorable pre-stroke terrain state. (Height sculpt already works via `import_images`, so restore itself is not at risk; only the snapshot-read is the open question.)
- Persisting terrain requires writing outside the scenario's own directory tree, or to a location the load path cannot resolve back through a `res://` `TerrainRef`.

## Design Notes

**Terrain persistence API (Terrain3D 1.0.1, confirmed via addon GDScript).** Save: `terrain.data.save_directory(absPath)` writes one `terrain3d_XX_YY.res` per active region, each containing height + control + color together. Load: assigning `terrain.data_directory = path` auto-loads the region `.res` files (the addon's reload idiom sets it to `""` first, then the path — do that if a stale in-memory region lingers). Because the flat region is imported in-memory by `TerrainPhase` (position 5) *before* `ScenarioLoad` (position 12) even parses the scenario, restore must happen after `_ctx.Scenario` exists and then trigger `NavObstacleManager.MarkDirty()` (its `_Process` rebakes from `terrain.generate_nav_mesh_source_geometry`), so the NavMesh reflects the restored height.

**Stroke snapshot for undo.** Restore is safe and demonstrated: build an `Array[Image]` of length 3 (`[height, control, color]`, indices `TYPE_HEIGHT=0`/`TYPE_CONTROL=1`/`TYPE_COLOR=2`) and call `terrain.data.import_images(images, regionOriginWorldPos, 0.0f, 1.0f)` then `terrain.data.calc_height_range(true)` — the same call family `TerrainPhase.cs:73` already uses. `regionOriginWorldPos = new Vector3(loc.X*span, 0, loc.Y*span)`, `span = get_region_size() * get_vertex_spacing()`, `loc = (Vector2I)data.Call("get_region_location", worldPos)`; a brush of radius r can straddle up to 4 regions, so enumerate `get_region_location` at `p ± r` on X/Z. The open question is the snapshot *read*: `Terrain3DData.get_region(loc)` → `Terrain3DRegion.get_height_map()/get_control_map()` (→ `Image`, `.Duplicate()`) is the expected C++ API but is not exercised in GDScript — confirm the getter names live via C# reflection. **Fallback if the CPU-Image getters are unreachable:** snapshot the whole `data` to a per-stroke temp dir via `save_directory` in BeginPaint and restore by re-assigning `data_directory` to that temp on undo (coarser and disk-backed, but demonstrated-working for a single-region alpha map). Either mechanism satisfies the AC.

**Shared undo stack.** `EntityPlacer._history` is a private `EditorHistory` today; expose it and pass it to `TerrainBrush` so both push onto one stack. `TerrainBrush._Input` already ignores Ctrl+Z (it only consumes 1-5/[ /]/LMB when active), so `EntityPlacer._Input`'s existing Ctrl+Z/Y handler (`:251-266`) pops the shared stack and runs whichever delegate (entity or terrain) is on top — interleaving is correct by construction. Post-F5 staleness of this shared history is DW-138's pre-existing hazard; do not solve it here.

**`_store_undo` disposition.** The red line means Terrain3DEditor's internal `_terrain` is treated as uninitialized at operation time. `SetupEditor` already calls `set_editor`/`set_terrain` once at init yet 6.1 saw the error persist, so re-assert both immediately before `start_operation` each stroke (mirroring the editor plugin's `_edit()` wiring). Verify live that this suppresses it. Since this story adds its own snapshot-based undo, Terrain3D's internal operation-undo is redundant regardless; if the re-assert does not fully silence the compiled-in `push_error`, document the exact residual and route around it (the disposition, not the presence of the call, is what the AC and epics.md require to be recorded in a code comment).

**Packaging path bookkeeping.** Keep terrain beside the scenario: for `…/scenarios/{stem}.json`, use `…/scenarios/{stem}_terrain/` and `TerrainRef = res://…/scenarios/{stem}_terrain/`. `Pack` zips those `.res` under `map/terrain/`; `DoImport` extracts them to `res://resources/data/scenarios/{manifest.Id}_terrain/` and rewrites the copied scenario's `TerrainRef` to match (the scenario is renamed to `{manifest.Id}.json` on import, so the terrain folder name must track `manifest.Id`). Writing under `res://` via `GlobalizePath` matches the existing scenario-save convention.
