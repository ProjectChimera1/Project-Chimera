## Intent

**Problem:** The `F5` Edit↔Play toggle (`GameState.Toggle`, `GameState.cs:36`) today only flips a mode enum and shows/hides authoring chrome; the sim just starts/stops ticking. On **return to Edit nothing in the simulation world resets** — `MainScene.ResetMatchOnReturnToEdit` (`MainScene.cs:1164`) clears only match-lifecycle/presentation state (`_gameOver`, `_playFrames`, `MatchStats`), so unit positions/deaths, spent resources, supply, fired triggers, timers, runtime buffs, and re-deployed `HeroStore` rows all persist into Edit. The *only* clean "authored start" today is a full `GetTree().ReloadCurrentScene()` (the perceptible build step UX-DR83 forbids). This story is NFR-1's unowned owner and closes the two 3.9-deferred handoffs (HeroStore additive-across-re-deploys with no return-to-Edit clear; render-slot re-materialization for the seamless no-restart round-trip).

**Approach:** **In-place reset-to-authored-start, no scene reload.** Add a Godot-free `SimulationHost.ClearForReset()` that restores every owned store to its post-construction state (so all capture-once presentation/system references stay valid — reconstructing the host would orphan ~30 cached aliases), then a thin `MainScene.ResetToAuthoredStart(bool preserveHeroProgress)` that clears, re-validates+re-applies the current in-memory `_ctx.Scenario` through the existing `ScenarioApplier.Apply`, re-mints the deployed hero profile via `HeroProfileLoader.LoadInto`, and recomputes `StartStateHash`. Route **both** F5 edges through it: entering Play starts the sim from a freshly-applied authored world (picking up trigger edits made in Edit); returning to Edit restores the authored board for editing and discards playtest hero progress unless a `PersistenceTestMode` flag is set. `ScenarioApplier.Apply` is additive/non-idempotent, so the clear MUST precede every re-apply.

## Boundaries & Constraints

**Always:**
- **Reset is in-place — clear the existing stores, never reconstruct the host.** Every presentation bridge (`MultiMeshBridge`, `BuildingBridge`, `ProjectileBridge`, `FogOfWarBridge`, `ResourceNodeBridge`, `MinimapBridge`) and UI system (`SelectionSystem`, `CommandCardSystem`) plus all `SceneContext` sim-spine aliases capture their store references **once** at Initialize; a swapped host silently orphans them. `ClearForReset` therefore mutates the store objects in place.
- **`ClearForReset` restores exact post-construction state.** Clear `World`, `Nodes`, `Resources`, `Buildings`, `Projectiles`, `CombatEvents`, `Heroes`, `Modifiers`, and `Fog`; reset `MatchStats`; reset the wrapped `SimulationLoop` tick counter + `LastChecksum` to 0 and the per-slot `AbilityCastSystem` cooldowns. A cleared store must byte-for-byte equal a freshly-constructed one (free-lists empty, counts/high-water-marks zeroed, SoA cleared, `EntityWorld` RNG re-seeded to `DEFAULT_RNG_SEED`). `ScenarioDirector` trigger/timer/variable state is reset by the re-apply's `ScenarioApplier.Apply → ScenarioDirector.LoadScenario` (`ScenarioApplier.cs:147`), not by `ClearForReset`.
- **Determinism is sacred and no golden moves.** clear + re-apply + re-mint from the same authored `ScenarioData` and profile MUST reproduce a byte-identical run: identical `SimChecksum` at every tick and an identical `StartStateHash`, versus a fresh boot-and-apply of the same scenario. `SimChecksum.AlgoVersion` (9), `CanonicalModelHash` (3), and `StartStateHash` (1) stay UNCHANGED and unbumped; the 18 SimChecksum replay goldens and `hero-start-state.golden.txt` stay byte-identical (this story folds NO new field into any hash — HeroStore's per-tick fold is still Story 3.13).
- **`HeroStore` gains a bulk clear and the reset re-mints from the deployed profile.** `ClearForReset` empties `HeroStore` (currently only per-slot `Destroy` + monotonic `Count`, the confirmed 3.9 gap); the re-apply records placed heroes into `ScenarioApplier.LastAppliedHeroes` and `HeroProfileLoader.LoadInto(_host.Heroes, applier.LastAppliedHeroes, profile)` re-mints them at the profile's authored `Level`/`Xp`. Re-deploying is thus idempotent (no stale live rows), closing the 3.9 additive-re-deploy defect.
- **Playtest hero progress is discarded on return-to-Edit unless `PersistenceTestMode`.** The reset takes `preserveHeroProgress`; default (`false`) re-mints the deployed profile's authored initial `Level`/`Xp` (discarding any runtime growth). When `true`, snapshot the live `HeroStore` `Level`/`Xp` per stable `HeroId` before clearing and re-mint those. Pre-3.13 there is no runtime XP growth so both branches coincide today; this is the tested seam Story 3.13 consumes.
- **Both F5 edges reset; entering Play reflects Edit-side edits.** Extend the existing `GameState.ModeChanged` handling (wired in `WinConditionPhase.cs:124`) so BOTH transitions call `ResetToAuthoredStart`: Edit→Play (clean authored start + trigger add/remove/enable now live via the re-apply's `LoadScenario`) then run; Play→Edit (authored board restored) then stop. The re-apply reads the live `_ctx.Scenario` the `TriggerEditorPanel` mutates in place (`TriggerEditorPanel.cs:228`), so trigger edits are live with no reload. Unit/ability edits remain applied by their existing auto-reload-on-save (`UnitCardPanel.Edit.cs:995`, `AbilityEditorPanel.cs:573`) — that is a save-time action, not the F5 loop, so it satisfies "no *manual* reload" without a per-toggle build step.
- **Fail closed on an invalid edited scenario.** The reset re-validates `_ctx.Scenario` via `ScenarioValidator` before `Apply` (the `Validated<ScenarioData>` is not retained past boot). If validation fails, ABORT the Edit→Play transition, keep the world in Edit unchanged, and surface the located error — mirroring the existing F5 unit-validation gate (`UnitCardPanel.Edit.cs:52`). Never enter Play on an invalid scenario.
- **Layer purity.** `ClearForReset` and every store `Clear`/`Reset` are Godot-free (`src/Core/**`, pure C#, no `using Godot;`, ascending-id iteration, fixed-point only, no wall-clock/RNG-drift). Only `MainScene.ResetToAuthoredStart` + the `ModeChanged` wiring touch presentation.

**Block If:**
- (none — the story ACs, UX-DR62's reset scope [positions, resources, supply, fired triggers, timers; hero XP discarded unless persistence-test], UX-DR83, NFR-1, and the 3.9 continuity contract fully determine the design.)

**Never:**
- Never reconstruct `SimulationHost` or use `GetTree().ReloadCurrentScene()` on the F5 toggle (orphans capture-once refs / re-runs bootstrap incl. `HeroPickerPhase` / is the forbidden perceptible build step). The reset is in-place.
- Never fold `HeroStore` into `SimChecksum` or bump `SimChecksum`(9)/`CanonicalModelHash`(3)/`StartStateHash`(1); never re-record the 18 SimChecksum goldens or `hero-start-state.golden.txt`. This story adds no hash field (per-tick HeroStore fold is Story 3.13).
- Never make `ScenarioApplier.Apply` idempotent by re-plumbing its additive `AddOre`/`Create`/`PlaceBuildingDirect` writes — the invariant is clear-then-apply, not apply-over-dirty.
- Never rebuild the editor persistence / faction-def-resolution / ability-registry paths to make unit/ability edits live on the F5 toggle without a save — out of scope; they already round-trip via auto-reload-on-save.
- Never seed the sim from wall-clock/RNG or leave any store partially cleared (a leaked SoA slot desyncs at tick 1 — the exact `StartCrystal`-class defect the checksum exists to catch).

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Reset reproduces a run | Apply scenario S, run N ticks with recorded inputs → checksum C1; then `ClearForReset` + re-apply S + re-mint, run same N inputs | Checksum C2 byte-identical to C1 at every checksum tick | No error |

| Return-to-Edit restores board | After a Play session (units moved/died, ore spent, triggers fired, buffs applied) press F5→Edit | All match state resets to authored start: positions, resources, supply, fired triggers, timers, modifiers; Edit shows the authored board | No error |
| HeroStore non-additive on re-deploy | Deploy profile P, F5→Play→Edit, F5→Play again (same P) | `HeroStore` holds exactly one row per placed hero each Play (re-mint after clear), never accumulating stale rows; `StartStateHash` identical across deploys | No error |
| Discard playtest XP | `PersistenceTestMode=false`, hero at a (hypothetically) grown level/XP at match end, F5→Edit | Reset re-mints the deployed profile's authored `Level`/`Xp` (discards growth) | No error |
| Preserve playtest XP | `PersistenceTestMode=true`, F5→Edit | Reset snapshots live `HeroId`→`Level`/`Xp` before clear and re-mints the snapshot (progress kept) | No error |
| Trigger edit live on next Play | In Edit add/remove/enable a trigger on `_ctx.Scenario`, F5→Play | The re-apply's `LoadScenario` rebuilds director state; the edited trigger set is active this Play, no reload | No error |

| Fallback (no JSON) scenario | `_ctx.Scenario` null (hardcoded `ApplyFallback` path), F5 round-trip | Reset uses `ApplyFallback` after clear; no triggers/timers to reset beyond `ClearForReset`; round-trips cleanly | No error |

## Design Notes

- **D-1 — Clear-in-place, not reconstruct.** Investigation confirmed every bridge/system/`SceneContext` alias captures its store reference once at Initialize (e.g. `MultiMeshBridge._renderWorld`, `SceneContext.World/Buildings/Heroes/...`, the `readonly` `ScenarioApplier._host`). Swapping `_host` orphans ~30 references and effectively re-runs `_Ready`. Clearing the store *objects* keeps every reference valid — the pervasive capture-once pattern makes this the strictly lower-risk path. The cost is that each store needs a correct, complete `Clear()`; the reset-reproduces-a-run golden fully guards completeness (a missed field diverges the checksum).
- **D-2 — Determinism guard is the keystone test.** `EntityWorld` is default-seeded (`DEFAULT_RNG_SEED`, no match-seed plumbing — `SimulationHost.cs:85-87`), so a correct `ClearForReset` makes clear+apply byte-equal to construct+apply. The Tier-1 test: apply S → run N recorded ticks → `C1`; `ClearForReset` → re-apply S → run same N → `C2`; assert `C1==C2` at every checksum tick. This is what lets Strategy-X in-place clearing be trusted, and it re-confirms the goldens don't move (no field folded).
- **D-3 — Both edges reset; the re-apply is the edits-live mechanism.** `ScenarioApplier.Apply` is additive (`AddOre`/`Create`/`PlaceBuildingDirect`), so it must run only against a cleared host. Running it on Edit→Play picks up trigger add/remove (director rebuilt via `LoadScenario`) and re-spawns from the current (post-save-reload) faction defs, so unit/ability edits already on disk are reflected. Enable/disable is already live (director reads `t.Enabled` off the shared `TriggerDefinition` class each tick). Running it on Play→Edit restores the authored board so editing never happens on a battle-scarred world.
- **D-4 — `PersistenceTestMode` seam is real but inert pre-3.13.** Runtime XP growth is Story 3.13; today a hero's level/XP is static, so discard and preserve produce identical values. The flag + the snapshot-before-clear branch exist and are Tier-1 tested (both routes exercised) so 3.13 hooks in with no re-architecture; default is discard (`false`).
- **D-5 — Fail-closed on invalid edits.** The `Validated<ScenarioData>` proof is discarded after boot (`ScenarioLoadPhase` consumes `r.Value` locally). The reset re-mints it via `ScenarioValidator` before `Apply`; on failure the Edit→Play toggle is vetoed (stay in Edit, surface the located error), consistent with the existing unit-validation F5 gate — never enter Play on invalid content.
