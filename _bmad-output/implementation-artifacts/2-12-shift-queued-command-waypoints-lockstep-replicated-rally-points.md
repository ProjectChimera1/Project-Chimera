## Story

As an RTS player,
I want to Shift-queue orders into waypoint chains and have rally-point changes ride the same replicated order stream as every other command,
So that multi-step orders work the way every RTS since WC3 works and rally state can never silently drift between lockstep peers.

## Why this matters (source-verified)

**Two long-standing gaps, one story.** Today there is **no shift-queue** anywhere (grep-confirmed: no `OrderQueue`/`CommandQueue`/`QueuedOrder`/`ShiftQueue` token exists in `godot/src` — this is greenfield, no partial scaffolding), and **rally points are a logged desync vector**. Rally state lives in the sim `BuildingStore` (`RallyPoint[]`/`HasRallyPoint[]`, `BuildingStore.cs:53-55`) but is **written by presentation off the command stream** — `SelectionSystem.SetRallyPoint` (`SelectionSystem.cs:725-735`, dispatched at `:304-305` on a building RMB) writes the store **directly**, with **no `EnqueueOrder`, no `OrderApplier`, no replay record**. It is then **read inside the deterministic tick** by `BuildingSystem.SpawnTrainedUnit` (`BuildingSystem.cs:227-239`): a set rally spawns the trained unit `Move→rally`, an unset one spawns `Stop`. So the issuing peer moves the unit and the other peer holds it → the folded `Position` diverges → fail-closed HALT. `deferred-work.md:8` names it verbatim ("Rally points are not lockstep-replicated … Route rally-set through the lockstep command stream"), and `gap-analysis-1.0-vs-wc3-2026-07-01.md:107-121` (Gap #7, MAJOR) adds the sharp detail: **Story 2.8 already routed `Train=11` through the wire, so MP training is real and the rally branch is a LIVE desync path, not latent** — and it is structurally un-catchable by the golden harness *because rally-set is not an order and can never be recorded in a replay*. Making rally an order is what makes it deterministic, replayable, and testable.

**The command pipeline is ready for both.** The shared `OrderApplier.Apply` (`NetworkCommand.cs:110-290`) is the single command→world dispatch, reached identically by the three apply sites — lockstep (`LockstepManager.cs:662-664`), replay (`ReplayPlayer.cs:178-180`), and offline (the `IssueX` seams in `SelectionSystem.cs`). The 11-byte `UnitOrder` wire (`NetworkCommand.cs:73-93`) already carries a building-targeting command (`Train=11`: `UnitId`=building, handled **before** the entity guard at `:129-133`) and packs secondary ints via `Fixed.FromRaw`. `UnitCommand : byte` runs 0–12 contiguous (`EntityWorld.cs:12-31`) → **id 13 is free**, and all three apply sites **already thread the `BuildingSystem? buildings` arg**, so a `SetRally=13` command inherits three-path parity for free (AC3). Story 1.12's `PatrolWaypoints` is a **per-entity cap-8 SoA ring folded into `SimChecksum`** (`EntityWorld.cs:83,324-330`; `SimChecksum.cs:109-123`) with an append-vs-replace precedent (`Patrol` vs `PatrolAppend`, `NetworkCommand.cs:208-256`) — the near-exact template for the new order queue (AC1).

**The two genuinely hard parts** are the two net-new surfaces: (1) **AC2 is an actual fold** — a per-entity order queue is *runtime-mutable mid-match* sim state, so per the standing **[[chimera-checksum-fold-timing-rule]]** it MUST fold into `SimChecksum` with `AlgoVersion 8→9` and **all 16 goldens re-baselined** (the 2.4a v6→7 / 2.6 v7→8 recipe — the exact opposite of 2.9a/2.11's authored-immutable NO-FOLD); and (2) **AC1's "dispatch on completion of the previous order" needs a DETERMINISTIC in-sim completion signal that does not exist today** — for a `Move`, the "arrived → Stop" transition happens in the **presentation layer** (`PathRequestSystem.cs:189-190`, `FlowFieldBridge.cs:154-161`, both `_Process`), and `MovementSystem` deliberately clears only the `Moving` flag, never `CommandState` (`MovementSystem.cs:75-83`). `EntityFlags.Moving` itself is **written by presentation** (`FlowFieldBridge`/`PathRequestSystem`/`SelectionSystem`, all `src/UI/`), so the queue must detect completion with its **own pure-sim `SqrDistance`-to-`CommandGoal` arrival check** (mirroring the sim-owned `CombatSystem.ResumeAttackMove:472-485` and `BuildingSystem.ClearWorkerBuild:438-452`), never the flag or the presentation transition.

_Covers: FR-74 (`epics.md:380,475` — match-feedback floor; shift-queue/rally slice). Depends on: 1.12 (`UnitCommand` vocabulary + `OrderApplier` + `PatrolWaypoints` ring — done). Determinism precedent (not a dep): 2.4a `AbilityCooldownTicks` fold, 2.6 `EffectiveArmor` fold._

## Acceptance Criteria

### AC1 — Shift-queued per-entity order ring, dispatched through the shared `OrderApplier` (epic AC1)

**Given** a unit is selected **When** I Shift+right-click three points (or Shift-issue attack-move/patrol/ability orders) **Then** a bounded per-entity order queue (SoA ring, cap 8) stores them and each order dispatches through the shared `OrderApplier` on completion of the previous one **And** a plain (non-Shift) order clears the queue and replaces it.

- **AC1.1** New per-entity SoA on `EntityWorld` holding pending orders: `OrderQueueCmd` (`byte[]`, the masked `UnitCommand`), `OrderQueueTargetX`/`OrderQueueTargetZ` (`int[]`, `Fixed` raw / packed id), and `OrderQueueCount` (`byte[]`), each sized `MAX_ENTITIES * MAX_ORDER_QUEUE` (ring/flat) / `MAX_ENTITIES` (count), with `const int MAX_ORDER_QUEUE = 8` (`EntityWorld.cs`, beside `MAX_PATROL_WAYPOINTS=8` at `:83`). This is **runtime state, NOT def-derived** — it follows the `PatrolWaypoints`/`AbilityCooldownTicks` posture (defaulted in `Create()`, mutated by systems), **not** the `ApplyUnitDefinition`/A2 posture (see Decision #1).
- **AC1.2** A **Shift** (queued) order is issued to the sim as a normal `UnitOrder` on the unchanged 11-byte wire with a **queued/append flag** set (Decision #2 — high bit of the `Command` byte); `OrderApplier` **appends** `(cmd, targetX, targetZ)` to the entity's ring instead of touching `CommandState`. A **plain** (non-flagged) order **clears the ring** (`OrderQueueCount[id]=0`) and then applies immediately through the existing switch (replace semantics).
- **AC1.3** A new `OrderQueueSystem` (`ISimSystem`) dispatches the head order when the current order **completes**, by **reusing the `OrderApplier` command→`CommandState` switch — no second dispatch path** (the epic's line-1145 / 1.12 structural-parity rule). It runs at **tick index 3** (after `MovementSystem`/2, before `AbilityCastSystem`) so arrival is fresh and a popped `CastAbility` fires the same tick (Decision + Task 4).
- **AC1.4 (the crux).** Completion is detected by a **deterministic pure-sim signal**, NEVER the presentation `Move→Stop` (`PathRequestSystem.cs:189-190`/`FlowFieldBridge.cs:154-161`) and NEVER `EntityFlags.Moving` (presentation-written in `src/UI/`). For a movement order it is a `SqrDistance(Position[i], CommandGoal[i]) <= arriveSqr` test computed in `Fixed` (mirroring `CombatSystem.ResumeAttackMove:472-485`, `AMOVE_ARRIVE_SQR` at `:69`, and `BuildingSystem.ClearWorkerBuild:438-452`); for a target order (AttackTarget/AttackBuilding/Follow) it is `CommandState[i] == Idle` (the target-loss transition the sim already writes, `CombatSystem.cs:253-254,299,413`); an ability cast is transient (completes immediately). See Decision #3.
- **AC1.5** Queue advancement, append, clear, and completion all run **inside the tick** on sim state (never in `SelectionSystem`/presentation) — the ring is `EntityWorld` state fed by wire orders, so live == replay == offline by construction (online orders are deferred via `LockstepManager.EnqueueOrder:236-245`, so the queue cannot live on the presentation side). Iteration is ascending-id; all math `Fixed`/int; no `float`/`Mathf`/`System.Random`/`Dictionary` enumeration/wall-clock in the new system.

### AC3 — Rally-point changes ride the `UnitOrder` wire, all three apply sites, loopback checksum-identical (epic AC3)

**Given** a rally point is set or changed on a building in an online or replay context **When** the change is issued **Then** it rides the `UnitOrder` wire format (a new `UnitCommand` id, no PROTOCOL/`ReplayRecorder.VERSION` bump if a spare id fits the existing byte) through all three apply sites (lockstep/replay/offline) **And** a two-client loopback run where both clients set rallies stays checksum-identical for 300+ ticks.

- **AC3.1** New `UnitCommand.SetRally = 13` (`EntityWorld.cs:12-31`; next free id, `byte`-backed, values 0-12 frozen). Wire: `UnitId` = buildingId, `TargetX`/`TargetZ` = rally ground point as `Fixed` raw (the `Move` encoding); it **fits the 11-byte `UnitOrder` unchanged** → **no `PROTOCOL_VERSION`/`ReplayRecorder.VERSION` bump** (`CommandApplyParityTests.cs:246` precedent). Handled in `OrderApplier.Apply` **before** the entity alive/ownership guard (like `Train`, `NetworkCommand.cs:129-133`), since `UnitId` names a building; it does its bounds + `Alive` + faction anti-cheat check then writes the store, and **never persists as a `CommandState`**.
- **AC3.2** Rally reuses the EXISTING sim store — `BuildingStore.RallyPoint[]`/`HasRallyPoint[]` already exist (`BuildingStore.cs:53-55`, allocated `:77-78`, full 64-slot capacity `MAX_BUILDINGS=64`). The two writes currently in `SelectionSystem.SetRallyPoint` (`:730-732`) MOVE into a new `BuildingSystem.SetRallyCommand(int buildingId, Faction expectedFaction, Fixed x, Fixed z)` (exec-tick handler, template `BuildingSystem.TrainUnitCommand:382-388`), invoked from the `OrderApplier` `SetRally` case via the already-threaded `buildings?` arg. The presentation pole marker (`BuildingBridge.UpdateRallyMarkers:299-322`) reads `HasRallyPoint` and needs **no change** — it "just works" once the store is populated deterministically.
- **AC3.3** `SelectionSystem.SetRallyPoint` is converted from a direct store write to a wire issue: `_lockstep?.EnqueueOrder(buildingId, UnitCommand.SetRally, Fixed.FromFloat(hit.X), Fixed.FromFloat(hit.Z)) ?? true` → offline applies now via `OrderApplier.Apply(_world, order, Faction.Player1, buildings: _buildSys)` (the `IssueTrainCommand`/`CommandCardSystem.cs:341-351` shape). The `Fixed.FromFloat` on the raycast hit is a **one-time issue-side quantization** (the local peer resolves its screen-ray, then ships the `Fixed` raw over the wire → every peer applies the identical value); this matches `IssueMoveCommand`/`EnqueueCommand:154` and is NOT a per-tick float call.
- **AC3.4** All three apply sites already pass `buildings`/`Buildings`/`_buildSys` (`LockstepManager.cs:662-664`, `ReplayPlayer.cs:178-180`, `CommandCardSystem.cs:346-350`), so `SetRally` is applied on every path with no new plumbing. `BuildingStore.Create()` (`:88-147`, does NOT reset rally today) gains a `HasRallyPoint[id]=false` reset — forward-safe for Story 2.13's `BuildingStore` recycling (harmless today under append-only, mandatory once slots reuse; the SoA-recycle rule).
- **AC3.5** **Loopback discharge (Decision #4).** Two in-process `SimulationHost`s are fed the **identical** SetRally (+ Train, so a unit actually spawns to rally) order schedule each tick via the `ApplyScheduleStep(host,i)` hook (template `AbilityCastScenario.cs:64-72`, `ServerBootstrapDeterminismTests.cs:38-54`) and their `SimChecksum` sequences are asserted `SequenceEqual` for **300+ ticks** + pinned by a committed cross-platform golden. ### AC4 — A 9th order on a full queue is rejected deterministically + emits a denial event for 11.9 (epic AC4)

**Given** a full 8-deep queue **When** a ninth order is Shift-issued **Then** it is rejected deterministically (no crash, no desync, denial feedback event emitted for 11.9 to consume when it lands).

- **AC4.1** The append path in `OrderApplier` (the queued-flag branch) checks `OrderQueueCount[id] >= MAX_ORDER_QUEUE` **before** writing; if full it **does not append** (no ring overflow, no crash) and the queue state is unchanged. The reject is deterministic — all peers see the same folded `OrderQueueCount` and reject identically (no desync). This mirrors `PatrolAppend`'s "route is full — silently ignore" (`NetworkCommand.cs:253`) but adds the event below.
- **AC4.2** A new `CombatEventType.OrderDenied` member (`CombatEventQueue.cs:8-21`; currently 6 members, none for denial) is emitted at the entity's position when the append is rejected (`CombatEventQueue.Push(CombatEventType.OrderDenied, world.Position[id])`, `:60`). Appending an enum member is **golden-safe and version-free** — the queue is NOT a `SimChecksum` input (`:14-20`; confirmed absent from `SimChecksum.Compute`). Story 11.9 consumes it when it lands; if 11.9 needs the entity id / reason, add a `CombatEvent` field then (Decision #6 — do not pre-build).
- **AC4.3** Emitting from the sim (`OrderApplier`/`OrderQueueSystem`) onto the presentation `CombatEventQueue` is the established pattern (`CombatSystem` already pushes combat events). The emission is presentation-only feedback; the **reject decision** is the deterministic, folded part.

## Decisions

**Baked in (deterministic-rule / forced-by-source / minimal-slice calls — applied, not re-asked):**

1. **The order queue is runtime sim state, folded — NOT authored/A2.** Like `PatrolWaypoints`/`AbilityCooldownTicks` (mutated during the match), it is defaulted in `Create()`, written by `OrderApplier`/`OrderQueueSystem`, and folded count-driven into `SimChecksum` — it is **NOT** written in `ApplyUnitDefinition` and **NOT** guarded by `ApplyUnitDefinitionGuardTest` (that is for def-derived fields). Coverage = the `SimChecksum` fold teeth + a `Create()`-reset recycle test. (The `CommandTarget`/`PatrolWaypoints` posture — `EntityWorld.cs:317,324` — not the `TagsOf`/`AttackDomainOf` authored-immutable posture.)
2. **One atomic fold `8→9`, all 16 goldens re-baselined** — mandated by AC2, executed via the 2.4a v6→7 / 2.6 v7→8 recipe exactly (fold code + AlgoVersion + changelog + re-pin + VersionStamp + coverage teeth + re-record + new golden, all one commit). This is the OPPOSITE of 2.9a/2.11's NO-FOLD; the fold-decision hinge ([[chimera-checksum-fold-timing-rule]]) = "fold when the array first becomes mutable mid-match" → an order queue is mutable mid-match → fold is correct and required.
3. **Wire stays 11 bytes; no `PROTOCOL_VERSION`/`ReplayRecorder.VERSION` bump.** `SetRally=13` (UnitId=building, TargetX/Z=point) + the queued/append flag both fit the existing `Command` byte / target fields → only `SimChecksum.AlgoVersion` moves. Do NOT widen `UnitOrder` (that forces `ReplayRecorder.VERSION 2→3`, the `GroundPoint` deferral in `deferred-work.md §2.4a`).
4. **Dispatch reuses the `OrderApplier` command→`CommandState` switch — no second dispatch path** (the 1.12 rule, epic line 1145). Refactor the switch body into a shared core that both the wire-entry `Apply` (append/clear wrapper) and the `OrderQueueSystem` (pop→apply-active) call, so the command→state mapping is single-sourced.
5. **`OrderQueueSystem` slots at tick index 3** (after `MovementSystem`/2 so arrival is fresh; before `AbilityCastSystem` so a popped cast fires same tick), pushing ability/modifier/combat/… down one. Update `SystemOrderTest` and the system-count log ("11 systems"→"12", `SimulationHost.cs:142`) in the same commit (the registration order IS the determinism contract, `:110-111`).
6. **Rally reuses the existing `BuildingStore` fields + presentation pole; AC3 adds only the deterministic write path** — the store, the spawn-consumer (`BuildingSystem.cs:227-239`), and the marker already exist and stay. Add the `BuildingStore.Create()` `HasRallyPoint` reset (forward-safe for 2.13).

**Recommended defaults (surfaced for Alec — the story is written for these; alternatives noted):**

- **D-1 — RALLY FOLD (recommended = FOLD, same 8→9 bump).** `RallyPoint`/`HasRallyPoint` are the one `BuildingStore` state read in-tick (`SpawnTrainedUnit`) that is NOT folded (`SimChecksum.cs:181-188` folds only `Alive`/`Health`/`ConstructionTimer`). Once rally is wire-driven it becomes genuinely mutable-mid-match sim truth → the fold-timing rule says fold it, and folding makes AC3's "checksum-identical" test have **direct teeth** (a rally divergence is caught immediately, not only transitively once a unit spawns and its `Position` drifts). Since the 8→9 bump happens anyway for the queue, adding rally to the building fold loop (`Mix` `HasRallyPoint` + `RallyPoint.X/Z.Raw` per building) is nearly free. **Recommended: FOLD rally in the same bump.** **Alternative:** NO-FOLD rally, relying on the deterministic wire write (both peers apply the same `SetRally` at the same tick → identical store) with divergence caught transitively via the folded trained-unit `Position` — cleaner diff, but the loopback test then only has teeth if it actually trains a unit.
- **D-2 — QUEUED/APPEND WIRE ENCODING (recommended = high bit `0x80` of the `Command` byte).** `UnitCommand : byte` uses only values 0-13 → bits 6-7 are free; a Shift-issued order sets `Command | 0x80` on the wire, and `OrderApplier` masks it (`var cmd=(UnitCommand)((byte)o.Command & 0x7F); bool queued=((byte)o.Command & 0x80)!=0;`) before the switch. Wire-only, never stored in `CommandState`, no wire growth, uniform across all order types. **Alternative:** distinct append-command ids per type (the `PatrolAppend=9` precedent — but 5+ new ids for a heterogeneous queue = id-bloat), or widen the wire (rejected — forces the `ReplayRecorder.VERSION` bump AC3 says to avoid).
- **D-3 — COMPLETION DETECTION (recommended = pure-sim `SqrDistance` arrival + `CommandState==Idle`).** The `OrderQueueSystem` computes its OWN `Fixed` `SqrDistance(Position, CommandGoal) <= arriveSqr` for movement orders (mirroring `ResumeAttackMove`/`ClearWorkerBuild`) and treats `CommandState==Idle` as completion for target orders. It MUST NOT read the presentation `Move→Stop` transition or `EntityFlags.Moving` (both presentation-touched in `src/UI/` → would diverge headless-golden vs live-client). **Alternative:** add a NEW sim-owned `Arrived`/`OrderComplete` `EntityFlags` bit set only by sim systems on arrival — more invasive (touches every arrival site) but gives a single uniform signal; deferred unless the per-type check proves fragile in review.
- **D-4 — AC3 LOOPBACK DISCHARGE (recommended = two in-process `SimulationHost`s + `SequenceEqual` 300+ ticks + committed golden).** The established sim-layer determinism proof (there is no Tier-1 two-real-sim network harness). **Alternative:** extend the Godot/DEBUG `LoopbackDesyncSelfTest.cs` to run real `SimulationHost`s and feed real checksums — a much larger, non-Tier-1, Godot-side lift; only if Alec wants a literal networked run.
- **D-5 — TERMINAL ORDERS IN A QUEUE (recommended = allow, naturally stall).** `Patrol`/`Follow` never complete (loop/track) and `Stop`/`Hold` are terminal; a queued one simply becomes the persistent state and the remaining queue never pops (WC3-consistent — a patrol ends a queue). **Alternative:** reject queuing terminal orders at issue time. Recommended: allow-and-stall (simpler, no special-casing).
- **D-6 — DENIAL EVENT PAYLOAD (recommended = `OrderDenied` carrying only Type+Position now).** Minimal `CombatEvent` shape; add an entity-id/reason field only when Story 11.9 actually needs it. **Alternative:** add the field now (speculative; 11.9 is not yet scoped).
