## Story

As a simulation engineer,
I want a sparse HeroStore (Struct-of-Arrays) keyed by a stable cross-match hero identity, with hero progression folded into the determinism checksums,
so that hero progression state is part of deterministic, MP-safe initial state and cannot silently desync.

## Context & Scope — read first

**This is the AR-12 hero-persistence backbone — the pure-sim data substrate every later hero feature stands on.** It is the *riskiest* Epic 3 story (the Epic-2 retro's D-3 flags it for a different-LLM / heightened code review) because it touches the determinism spine. Read this whole section before writing code; the determinism posture here is subtle and precedent-bound.

**What 3.2 delivers (the whole story):**
1. **`HeroStore`** — a net-new, pure-C# **sparse SoA** (no `using Godot`, `Fixed` 16.16 for gameplay numerics, ascending-order iteration) keyed by a **stable cross-match hero identity** that is explicitly **NOT** the recycled `EntityWorld` id. Structurally a clone of the Story-2.13 `BuildingStore` (monotonic `Count` + LIFO free-list + generation-counter ABA-armor + `PackRef`/`TryResolveRef`).
2. **The stable-identity contract** — the identity type + assignment/persistence semantics that Stories 3.7 and 3.9 consume. (M2 offline decision per AR-12: "the stable-identity decision must still be made in M2.")
3. **A NEW canonical `startStateHash`** (its own hash + AlgoVersion, distinct from `CanonicalModelHash` and `SimChecksum`) over the init-time state **including HeroStore**, computed once at match start, with a determinism golden. **This is 3.2's primary determinism deliverable** — the init-state MP-safety guarantee (the StartCrystal-desync lesson, applied to heroes).

5. **A fenced companion fix (from Alec, this session): the game launches fullscreen** so playtesting looks like a game instead of a cramped window (see AC4 / Task 7). This is a `project.godot` config-only change, **independent of all sim work** — called out separately so the determinism scope stays clean.

**The determinism posture — READ THIS (it is the headline decision, D-1):**
The epic's Story-3.2 AC2 says "HeroStore contents are folded into `SimChecksum`." But **Story 3.13 AC2 *also* explicitly owns that fold** ("when the HeroStore level/XP arrays first become mutable → fold into `SimChecksum` with one AlgoVersion bump and all goldens re-baselined explicitly; revival state from 3.14 reserves its fields in this same fold"). In 3.2 **no system mutates HeroStore mid-match** — the XP runtime is 3.13, load is 3.9. Per the standing checksum-fold-timing rule (*"fold a new sim array into `SimChecksum` / re-baseline goldens ONLY when it first becomes mutable mid-match; dormant arrays = no fold"*) and the exact **2.2a→2.2b precedent** (2.2a built the effective-stat arrays dormant, `SimChecksum.cs` untouched, AlgoVersion stayed 5, all goldens byte-identical; 2.2b did the fold when they became mutable), **3.2 does NOT fold HeroStore into the per-tick `SimChecksum`.** 3.2 delivers the init-state guarantee via the new `startStateHash` (AC2/AC3) and the SoA + identity + ascending-iteration contract; the per-tick `SimChecksum` fold + AlgoVersion bump + golden re-baseline lands at **3.13** exactly where the epic puts it. This keeps 3.2's fence movement purely **additive** (a new `StartStateHash` v1; `SimChecksum` stays 9, `CanonicalModelHash` stays 3) — the safest possible posture for the riskiest story. **See D-1 for the alternatives (fold-now) if Alec vetoes.**

## Acceptance Criteria

**AC1 — HeroStore is a pure-C# sparse SoA keyed by a stable, non-recycled hero identity.**
`HeroStore` is a net-new struct-of-arrays under `godot/src/Core/` (or `src/Core/Definitions/`) with **no `using Godot`**, using `Fixed` (16.16) for any numeric *gameplay* state and plain `int`/`ulong` for identity/bookkeeping, **indexed and iterated in ascending order**. It is keyed by a **stable hero identity** that is **NOT** the recycled `EntityWorld` id and **NOT** the raw HeroStore slot index — a stable, content-/profile-defined key (D-4) that **survives across matches and across `EntityWorld` id recycling**. The store follows the Story-2.13 `BuildingStore` template: monotonic `Count` (the fold/iteration bound), LIFO free-list (unfolded), a per-slot generation counter (unfolded) bumped on reuse, `Create`/`Destroy` with double-free guards and explicit recycle-time field resets, and a `PackRef(slot)`/`TryResolveRef(packed,out slot)` generation-stamped handle so a stale cross-tick reference resolves **false** rather than silently retargeting a new hero. A `ProjectChimera.Sim.Tests` suite proves: minting assigns a stable identity distinct from the entity id; a recycled slot carries **none** of the prior hero's state; and a stale packed handle fails to resolve after recycle.

**AC2 — HeroStore is covered by the determinism checksums, ascending-identity order (init-state now; per-tick fold deferred to 3.13).**
Per D-1 (recommended = defer): HeroStore contents are folded into the **init-time `startStateHash`** (AC3) deterministically **in ascending-identity order**, alongside the canonical scenario init state — and two runs from identical HeroStore input produce a **byte-identical** result (golden test passes). The ascending-identity **iteration contract** HeroStore exposes for checksum folding is established and unit-tested here so Story 3.13 flips on the per-tick `SimChecksum` fold with no re-derivation. The per-tick `SimChecksum.Compute` fold + AlgoVersion bump is **deferred to Story 3.13** (where heroes first mutate mid-match), documented in-code and in `deferred-work.md`. *(If Alec picks D-1 alt A or B, this AC becomes a live `SimChecksum` fold — see D-1.)*

**AC3 — a NEW canonical `startStateHash` over the full init-time state including HeroStore.**
A **new, distinct** canonical hash (`StartStateHash`, its own `AlgoVersion` starting at 1, reusing the FNV-64 primitives — **not** extending `CanonicalModelHash` and **not** `SimChecksum`, per D4-C) is computed **once at match start** over the **canonical init-time state** — the scenario content model **plus** HeroStore contents — using `Fixed.Raw` canonical integers (never a post-spawn `EntityWorld` float snapshot, which would reintroduce `Fixed.FromFloat` producer-divergence). Two runs from identical init data produce a **byte-identical** `startStateHash`; a changed HeroStore (added hero, changed level/XP) changes it (teeth test). It is pinned two ways (an independent hand-computed FNV-64 pin + a recorded model-layout pin), mirroring `CanonicalModelHash`'s pin discipline. Its value is computed and pinned in 3.2; **wiring it into the network Ready-packet handshake is deferred to Epic 9** (D-3).

**AC4 — the game launches fullscreen (fenced companion fix).**
Running the project launches into a full-screen game window (not the default 1152×648 windowed view) so playtesting reads as a game and the HUD fills the screen without the cramped/"scroll to see things" feel. Implemented as a `project.godot` `[display]` block only (D-9); no `.cs`, no scene, no sim file changes. The always-visible HUD (top-left readouts, bottom-left controls, bottom-right minimap, center-top stall banner) renders correctly at the fullscreen size (it is corner-anchored — verified). `/godot-verify` (or a manual launch) confirms the game opens fullscreen with the HUD correctly placed.

**AC5 — clean scope, determinism fence intact, verification green.**
`SimChecksum.cs` and `CanonicalModelHash.cs` are **unchanged** (AlgoVersion stays **9** / **3**); all **17 existing goldens are byte-identical**; the `ExpectedV9Hash` and `ExpectedCanonicalHash` pins are **not** re-recorded. The only version-stamp movement is the **additive** new `StartStateHash` v1 (+ its pin + `VersionStampConsistencyTests` entry). `dotnet build godot/godot.csproj` → **0 errors** (no new warnings; the 3 pre-existing CS8632 are unrelated); the release analyzer gate (`-p:ChimeraRelease=true --no-incremental`) → **0 errors / 0 RS0030** (HeroStore is sim code — it is in-scope for the analyzer, so keep it `Fixed`/int-only, no `float`, no `Dictionary` enumeration, no `System.Random`). Tier-1 grows by the new HeroStore + startStateHash tests and stays **green**. `git diff --stat` is confined to `src/Core/**` (HeroStore + startStateHash + EntityWorld link + UnitDefinition designation), `ProjectChimera.Sim.Tests/**` (new tests + 1 new golden + csproj registration), `project.godot` (the `[display]` block only), and workflow tracking — **zero** changes to `SimChecksum.cs`, `CanonicalModelHash.cs`, any existing golden `.txt`, the wire/replay code, or any `src/UI`/scene/presentation file (except none — the fullscreen fix is `project.godot`-only).

(3) The init-state MP-safety guarantee (mismatched hero loadouts desyncing from tick 1 — the StartCrystal lesson) is delivered by `startStateHash` (AC3), which is where it belongs.   - **Alternative A (full fold now — the 2.12 template):** fold HeroStore into `SimChecksum.Compute`, `AlgoVersion 9→10`, re-baseline all 17 goldens + add 1 hero golden, re-pin `ExpectedV9Hash→ExpectedV10Hash`, add coverage teeth.   - **Alternative B (inert fold now):** fold HeroStore into `SimChecksum.Compute` as an **id-keyed sparse loop with no count header**, so an empty HeroStore mixes zero bytes → all 17 goldens stay byte-identical, `AlgoVersion 9→10`, + 1 hero golden for teeth. Mechanically sound (verified: `Mix(0)` is not a no-op, but a *no-header, key-first* loop over 0 rows mixes nothing) and satisfies 3.2-AC2 literally while keeping goldens byte-identical — but it is a **novel** deviation from the codebase's count-header fold convention (reviewer-surprise risk in the riskiest story) and bumping AlgoVersion here mildly conflicts with 3.13 AC2's "one bump."   - Net: **A** and **B** satisfy 3.2-AC2's literal `SimChecksum` text now; **C (recommended)** honors the fold-timing rule + the 2.2a→2.2b precedent + 3.13 AC2, delivering the coverage via `startStateHash` and deferring the per-tick fold. All three are determinism-correct (an immutable store cannot cause a false mid-match desync either way).

- **D-2 (startStateHash composition) — a NEW `StartStateHash` static class (FNV-64), folding the `CanonicalModelHash` value as the content seed THEN HeroStore rows ascending-by-identity (each row via `Fixed.Raw`/int).** *(Recommended.)* This is DRY (does not re-derive `CanonicalModelHash`'s slot/node/building/unit walk), keeps `CanonicalModelHash` at v3 untouched, and yields a single init-state hash that is a strict superset of content = "full init-time state including HeroStore" (AC3). Own `AlgoVersion` (mixed first, so a bump moves the value even with no field change — mirror `CanonicalModelHash.cs:44`). Sentinel `0→1` so a valid state never hashes to the fail-open value. **Alternative:** fold the raw scenario init state (slots/nodes/buildings/units) directly + heroes — rejected (duplicates `CanonicalModelHash` logic, two sources of truth for the content walk).

- **D-3 (startStateHash handshake wiring) — 3.2 computes + pins `startStateHash`; wiring it into the network Ready-packet + server attestation is DEFERRED to Epic 9 / M5.** *(Recommended.)* Mirrors how `CanonicalModelHash` landed (computed/pinned in Story 1.7; the multi-hash server-attested handshake is AR-18 / Epic 9) and honors D4 decision #8 ("startStateHash machinery + multi-hash handshake + 2-player generalization defer to M5"). 3.2 delivers the value + determinism golden; do **not** add it to `TickCommandPacket`/`MakeReady` or bump `PROTOCOL_VERSION`. **Alternative:** wire it into the Ready packet now — rejected (drags in the wire-format bump + server-attestation redesign that Epic 9 owns; would move `PROTOCOL_VERSION` off 1).

- **D-4 (stable hero identity type) — `ulong` (recommend a thin `readonly struct HeroId { public readonly ulong Value; }` for type-safety), profile-assigned, decoupled from the entity id.** *(Recommended.)* Forced by three constraints: the fold needs a **total order** (ascending-identity), SoA discipline is int-only, and it must serialize cleanly into `PlayerProfile` and produce a byte-identical `startStateHash` across the M2-local and M5-server producers. `ulong` gives ample space for a profile-assigned monotonic id (or a deterministic hash of profile-id + hero-slot); folds as two `Mix(int)` (low/high), like `SimRng` state. **Multiple saved heroes per player** (FR-7e) means the identity cannot be just the unit-type — it is per-save-slot, assigned at hero creation/first-save (the assignment mechanism itself is 3.9; 3.2 defines the *type + contract* and lets tests set it). **Alternative:** `int` — rejected (tighter space; a profile-id×slot hash wants 64 bits). A `struct HeroId` wrapper vs a bare `ulong` is the minor call; the struct prevents accidental mixing with entity ids (recommended).

- **D-5 (HeroStore store template) — clone Story-2.13 `BuildingStore`: monotonic `Count` fold-bound + LIFO `_freeList` (unfolded) + `Generation[]` (unfolded, bumped on reuse) + `PackRef`/`TryResolveRef` ABA-armor + double-free-guarded `Destroy` + explicit `Create`-time resets.** *(Recommended.)* HeroStore's requirements map onto BuildingStore 1:1: sparse rows, recyclable slots, and a **stable cross-tick reference that must resolve false when stale** (never silently retarget a new hero). `ProjectileStore` is too weak (slot *is* the identity, no ABA armor); `ModifierStore` is the wrong keying model (owner-entity-keyed, dies with the entity — a hero identity must *survive* its entity). **Alternative:** a bespoke store — rejected (reuse the proven 2.13 pattern; `PackRef`/`TryResolveRef` is exactly the generation-armor the hero identity link needs).

- **D-6 (schema scope) — build `{HeroId, EntityLink, Level, Xp}` LIVE; DOCUMENT the reserved 3.13-fold fields; do NOT pre-declare inventory.** *(Recommended.)* `Level`/`Xp` must exist now because Story 3.9 loads them as deterministic init state (upstream of the 3.13 XP runtime) and `startStateHash` must cover them. Do **not** front-load inventory: the fold cost is triggered by first *mutation*, not declaration, so pre-declaring `Inventory[]` saves no fold — 3.15's `ItemStore` fold (#2) lands regardless, and 3.15 hasn't designed the shape (default-6 slots, per-scenario-configurable, charges possibly on the item not the hero). The genuine pre-provisioning that *does* pay off: **specify the reserved field set (`Alive`/`AwaitingRevival`, `RevivalTimer`, revive-location/building-link) in the schema contract** so Story 3.13 reserves the exact right columns in its co-timed fold (3.13 AC2 already reserves 3.14's revival fields to avoid a second bump). Stat growth, item effects, energy/mana are **ModifierStore/existing entity SoA**, not HeroStore accumulators; leveling curve / xp-gain / signature+ultimate slots / xp_bounty / revival curves are **`UnitDefinition`/manifest DEFINITION data**, not per-instance store fields. **Alternative:** full "fold once" schema — rejected (see D-1; you'd have to fold the dormant arrays now, violating the fold-timing rule, for a single saved re-baseline you'll likely re-do when 3.15 designs items).

- **D-7 (hero designation) — a dedicated orthogonal `is_hero` bool on `UnitDefinition` (lenient-loader-safe), gating HeroStore-row minting at spawn; the hero authors `DamageType.Hero`/`ArmorType.Hero` (already reserved by Story 1.6).** *(Recommended.)* Mirrors the Story-2.11 `Tags` precedent (an orthogonal axis added to avoid abusing an existing enum). A hero is orthogonal to the movement archetype (a hero may be melee or ranged), so it must **not** be a 7th `UnitCategory` (which would also trip the enum-indexed-array touch-site rule — `[[chimera-enum-indexed-array-touch-sites]]`). Lenient-loader constraint: a nullable/settable auto-prop, no enum-typed field on that path. In 3.2 the designation + the minting API + a test that exercises it; the full **load-and-populate** path (from `PlayerProfile`) is 3.9. **Alternative:** a `Tags` flag (`"hero"`) reusing 2.11's `ParsedTags` — acceptable and slightly more composable; the plain `is_hero` bool is simpler and unambiguous. Either is fine; recommend the bool for clarity.

- **D-8 (EntityWorld↔HeroStore link) — `EntityWorld.HeroIndex[entityId]` stores a generation-stamped HeroStore handle (`PackRef`), defaulted to the "no hero" sentinel in `Create()` (recycle-trap), NOT in `ApplyUnitDefinition`; plus a reverse `HeroStore.EntityId[row]` for kill-attribution.** *(Recommended.)* The link is **runtime state** (established when a hero spawns and a row is minted), not authored def data — so it follows the `PatrolWaypoints`/`OrderQueue` posture (defaulted in `Create`, set by the spawn/mint path), **not** the A2 def-mapper posture, and needs its own `RecycledSlot_CarriesNoPriorHeroLink` teeth (the sole coverage for an unfolded field, per the guard-test convention). - **D-9 (fullscreen) — add a `project.godot` `[display]` block: borderless fullscreen `mode=3` + base viewport `1920×1080` + `stretch/mode="canvas_items"` + `stretch/aspect="expand"`; NO runtime toggle.** *(Recommended.)* `mode=3` (a borderless full-screen *window*, not exclusive) is the most game-like and does not fight the MCP `/godot-verify` screenshot path the way `mode=4` (exclusive) does. ### The determinism architecture (read before touching any hash)

Three distinct hashes exist / are created; keep them straight:

| Hash | Kind | AlgoVer | Covers | 3.2 action |
|---|---|---|---|---|
| **`SimChecksum`** (`src/Core/SimChecksum.cs`) | per-tick, FNV-1a **32-bit** | **9** | live sim state each tick (EntityWorld/BuildingStore/ResourceStore/Modifier/SimRng) | **UNTOUCHED** (fold deferred to 3.13 — D-1) |
| **`CanonicalModelHash`** (`src/Core/Definitions/CanonicalModelHash.cs`) | init, FNV-**64** | **3** | parsed content model (`ScenarioData`: slots/nodes/buildings/units + start resources/base pos) | **UNTOUCHED** (heroes aren't in `ScenarioData`) |
| **`StartStateHash`** (NEW, `src/Core/Definitions/StartStateHash.cs`) | init, FNV-64 | **1 (new)** | full init state = `CanonicalModelHash` seed + HeroStore | **CREATE** (AC3) |

- `SimChecksum.Compute` is one running FNV-1a accumulator via `Mix(hash,int)`; it does **not** fold its own `AlgoVersion` (so a bump alone moves nothing). Fold order is by array index (ascending id). The `ExpectedV9Hash = 0xFD72E97E` pin lives in `SimChecksumCoverageGuardTest.cs:123` (**not** ScenarioApplierTests). **You are not editing this file.**
- `CanonicalModelHash.Compute(ScenarioData)` is FNV-64 (offset/prime `:36-37`), mixes `AlgoVersion` **first** (`:44`), `OrderBy`s every collection over a total order of folded fields, folds numerics as `Fixed.FromFloat(v).Raw`. `ToWire(ulong)→uint` (`:108-112`) makes the 32-bit wire hash. Reference for adding a field = the StartCrystal fold (sort key `:56` + byte stream `:62` + version bump, Story 2.9b). **You are not editing this file either** — you *reuse its output as a seed* (D-2) and *copy its FNV-64 idiom* into `StartStateHash`.

The architecture (`game-architecture.D4-briefing.md:68`) mandates "pre-apply over the canonical MODEL — never over post-`ApplyScenario` state that passed through `Fixed.FromFloat`," because the M2-local and M5-server producers would otherwise diverge on float round-trips.
