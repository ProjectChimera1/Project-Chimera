## Intent

**Problem:** `UnitDefinition`/`BuildingDefinition` costs are two hardcoded fields (`cost_ore`/`cost_crystal`); `ResourceStore` hand-duplicates an Ore API and a byte-identical Crystal API; and no scenario can declare resources beyond these two. `BuildingDefinition.ConstructionCost` is already a computed `Dictionary<string,int>` placeholder (Story 4.1) whose own doc comment defers "the real authored sparse schema" to this story. Building placement (`QueueWorkerBuild`/`GetBuildingCost`) also only ever charges/refunds ore — crystal is silently never charged for buildings, a latent gap.

**Approach:** Add an authored sparse `cost` map (`Dictionary<string,int>`, JSON keys are resource ids) to `UnitDefinition` (inherited by `BuildingDefinition`), falling back to `cost_ore`/`cost_crystal` when `cost` is absent (back-compat, per the epic's own technical decision). Add a scenario-declared, ordered `ResourceDefinition` registry (id/display/starting-amount/collection-model) as authoring metadata for future resources (mirrors Story 4.1's "authored, validated, not yet wired" `ProducesCategory` precedent) — validated for internal well-formedness by `ScenarioValidator`. Generalize `ResourceStore`'s check/spend/refund call sites in `BuildingSystem` to operate on the sparse cost map via new generic `CanAfford`/`Spend`/`Add` overloads, WITHOUT restructuring `ResourceStore`'s internal `Ore[]`/`Crystal[]` arrays (no scenario in this epic introduces a third spendable resource; a real N-array runtime restructure is deferred to whichever future story first needs one).

## Boundaries & Constraints

**Always:** `UnitDefinition.ResolvedCost` is `Cost` verbatim when `Cost` is non-null (even if empty ⇒ free), else `{ "ore": CostOre, "crystal": CostCrystal }` with zero-valued entries omitted — the exact logic `BuildingDefinition.ConstructionCost` already uses today, generalized to Units (training cost) not just Buildings (construction cost); `BuildingDefinition.ConstructionCost` becomes `=> ResolvedCost` (name kept, no consumer breaks). `ResourceStore.CanAfford`/`Spend`/`Add(Faction, IReadOnlyDictionary<string,int>)` route "ore"→existing `*Ore` methods and "crystal"→existing `*Crystal` methods (never touch `Ore[]`/`Crystal[]` directly) so every untouched call site (`AbilityCastSystem`, `BuyItemCommand`, `ReviveHeroCommand`, `AiOpponentSystem`) keeps compiling and behaving byte-identically. `Spend` is atomic: `CanAfford` first, spend only if every key affords (mirrors the existing check-all-then-spend-all convention already used at every cost site in this file). Cost-map amounts quantize via `Fixed.FromInt` (exact for the `int` cost type — byte-identical to today's `Fixed.FromFloat` of an integer-valued cost). `ResourceCostValidator` (new, mirrors `TechTreeValidator`'s doc/shape, additive to `FactionDefinition.LoadFromFile`'s existing aggregate `errors` list) rejects, for every authored `Cost` entry: a key not in `{"ore","crystal"}` (located: entity id + offending key + "no runtime resource registered for it yet"), or a value `< 0` or `>= 32768` (mirrors `UnitDefinitionValidator.CheckCost`). `ScenarioData.Resources` (new, `ResourceDefinition[]?`, JSON `"resources"`, omit-when-null like `PersistenceManifest`) is validated by `ScenarioValidator` when non-null: non-empty unique `Id` per entry, finite non-negative `StartingAmount` — first-fail, same pattern as its other checks. `BuildingSystem.GetBuildingCost`'s new `IReadOnlyDictionary<string,int>` return type is consumed identically at both its call sites (`QueueWorkerBuild`'s spend/refund, `CommandCardSystem.RefreshWorkerCard`'s display) — no third call site exists. `SimChecksum`/`AlgoVersion`/`SimChecksumCoverageGuardTest`/every golden file stay byte-identical (no fold, no version bump — `ResourceStore`'s hashed arrays are untouched).

**Block If:** N/A — scoped to fully-specified files; the one open design question (whether cost-map referential integrity can be checked against the scenario's declared registry) is resolved below (Design Notes), not left open.

**Never:** Do not restructure `ResourceStore`'s internal `Ore[]`/`Crystal[]` arrays into an N-sized structure, and do not touch `SimChecksum`'s resource fold or `SimChecksumCoverageGuardTest` — no story in this epic spends a third resource, so there is nothing to prove coverage of yet. Do not extend the sparse-cost-map schema to `AbilityDefinition`/`ItemDefinition`/`RevivalRule` costs (three structurally different cost shapes — flat, shop, and per-level curve — left untouched; `AbilityCastSystem`/`BuyItemCommand`/`ReviveHeroCommand` keep using `CostOre`/`CostCrystal` directly). Do not touch `EntityPlacer.cs`'s separate, pre-existing hardcoded `BUILDING_COSTS` float array (unrelated debt, no `BuildingDefinition` read at all today). Do not wire `ResourceDefinition.StartingAmount`/`CollectionModel` into `ScenarioApplier` (authored/validated/available this story, NOT yet consumed — the `BuildingDefinition.ProducesCategory` precedent); starting balances stay on `ScenarioPlayerSlot.StartOre`/`StartCrystal`, untouched. Do not add cross-file validation of a cost-map key against `ScenarioData.Resources` (see Design Notes) or touch `FactionWriter.cs`'s editor round-trip (still writes `cost_ore`/`cost_crystal`; authoring a sparse `cost` map via the Creation Suite UI is a future editor story).

## Design Notes

**Why `ResourceCostValidator` only recognizes `{"ore","crystal"}`, not the scenario's declared registry:** `FactionDefinition.LoadFromFile` validates one faction file in isolation (no scenario context — a faction JSON is reused across scenarios, exactly like today's Ore/Crystal). `ScenarioData.Resources` is declared per-scenario. Cross-referencing a cost-map key against a *specific* scenario's registry would require threading the resolved scenario into the faction-load gate (or vice versa) — a distinct, larger architectural change (`ScenarioValidator` is the sim's single fail-closed pre-tick gate and today has zero `FactionDefinition` awareness by design). Since no story in this epic ever introduces a third *spendable* resource (Crystal already has runtime backing; Story 4.7 makes it producible, not new), this story validates cost-map keys against the two resource ids that actually have `ResourceStore` backing today. A creator MAY still declare additional `ResourceDefinition` entries (validated for internal well-formedness) as forward-looking scenario metadata; no unit/building cost can reference one until a future story backs it with real balance storage AND extends this validator's known-id set accordingly.

**Why `ResourceStore`'s arrays aren't restructured into `Fixed[][]`:** `SimChecksumCoverageGuardTest` reflects `Ore`/`Crystal` as named public fields and the pinned `KnownWorldState_ProducesPinnedV12Hash` test writes them directly (`resources.Ore[(int)Faction.Player1] = ...`). Replacing them with an N-sized jagged structure would force a golden re-baseline and a reflection-guard rewrite for a capability nothing in this epic exercises yet — pure risk with no corresponding acceptance criterion. The thin `CanAfford`/`Spend`/`Add(cost map)` wrapper delivers the authored generalization (sparse maps, back-compat, validation) the epic asks for without touching the proven, pinned storage layer.
