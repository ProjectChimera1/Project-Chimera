## Intent

**Problem:** Story 3.8 gave a creator a per-scenario `PersistenceManifest` + the shape-only `PlayerProfileShape` it derives, but there is no way to actually *save a hero to disk, list saved heroes, or load one into a custom game* — and no value-bearing `PlayerProfile`, no offline `LocalProfileSource`, and no apply path minting the loaded level/XP into `HeroStore` as deterministic initial state. Story 3.2's `StartStateHash` already folds `HeroId`/`Level`/`Xp` but nothing ever mints a hero, so the "heroes persist between custom games as MP-safe initial state" half of AR-12 (M2, offline) is unreachable.

**Approach:** **Offline rail + apply + player-facing picker.** (1) A Godot-free value-bearing `PlayerProfile` (stable `ProfileId`, hero identity `HeroDefId`/`FactionId`, card metadata, and persisted attribute values stored as integer raws — never floats) plus a Godot-free `LocalProfileSource` disk rail (inject a directory; JSON list; `LoadAll`/`Save`/`Delete`, mirroring `SettingsManager`'s pattern), pointed at `user://hero_profiles` by the Godot layer. (2) A Godot-free `HeroProfileLoader` that mints the deployed profile into `HeroStore` (`Mint(HeroId, entityId, level, Fixed xp)`) for the scenario's placed hero entities *before* `StartStateHash.Compute` runs, with a **deterministic `HeroId` = FNV-64 of `ProfileId`** so re-loading the same profile reproduces a byte-identical `StartStateHash`. `StartStateHash.cs`/`SimChecksum`/`CanonicalModelHash` are NOT modified and NOT re-versioned. (3) A player-facing `HeroPickerOverlay` (3.1 kit: slot cards from `Panel`+`Readout`+`Progress(Xp)`+`Tag`, `ChimeraDialog` confirm on Overwrite/Delete) shown at the **offline "Play Skirmish" start** only when the loaded scenario's manifest is `Enabled`, offering Deploy / Save / Overwrite / Delete + a non-blocking "Play without a saved hero", mounted via a new `HeroPickerPhase` that intercepts the skirmish launch.

## Boundaries & Constraints

**Always:**
- **The loaded profile is applied as DETERMINISTIC INITIAL STATE only.** Heroes are minted into `HeroStore` (via `HeroStore.Mint`) *before* `MainScene` computes `StartStateHash`, so the persisted `Level`/`Xp` fold into that hash automatically (StartStateHash already walks `Id.Value`/`Level`/`Xp.Raw` in `FoldOrder()` ascending order). Loading the same profile into the same scenario twice yields a **byte-identical `StartStateHash`** (MP-safe). Never apply a mid-game snapshot; only init-eligible attributes (`hero.level`, `hero.xp`) are carried.
- **`HeroId` is minted deterministically** = `FNV-64(ProfileId)` wrapped in `HeroId`. `ProfileId` is a stable string assigned by `LocalProfileSource` at save time and persisted, so the same saved profile always yields the same `HeroId` → reproducible hash. `HeroId`s are unique across live rows because `ProfileId`s are unique; a `Mint` returning `-1` (duplicate live id or full store) is handled deterministically (skip that hero + log) with no partial-state divergence.
- **XP round-trips as an integer raw** (`Fixed.Raw`), never a float. The profile serializes `hero.xp` as the `Fixed.Raw` `int`; apply reconstructs `Fixed` from that raw. `hero.level` serializes as its `int`.
- **The picker is offline-Play-Skirmish only, and manifest-gated.** It appears only when the loaded `ScenarioData.PersistenceManifest?.Enabled == true`; otherwise the skirmish launches straight to Play exactly as today. A profile is shown **selectable (compatible)** for the scenario when the scenario places a hero `ScenarioUnit` whose `UnitId == profile.HeroDefId`; otherwise the slot card is greyed/non-deployable. Apply is the authoritative gate: it mints only for spawned entities whose `UnitDefinition.IsHero` and whose `UnitId` matches the deployed profile.
- **Reuse the offline persistence + UI machinery, do not rebuild it.** Disk IO mirrors `SettingsManager` (`System.Text.Json` + `File` over a Godot-globalized `user://` path). The picker composes only from the 3.1 kit (`ChimeraComponents.Panel`/`Button(Danger)`/`Readout`/`Progress(ProgressVariant.Xp)`/`Tag`, `ChimeraListRow`+`ListRowGroup` for single-select, `ChimeraDialog.Create(...).AddConfirm(danger:true)/AddCancel` for destructive confirms, `ChimeraToastHost` for "Saved" feedback) with no new primitives unless a missing one is logged. Portrait uses `ChimeraMark` (procedural sigil) as the asset-free placeholder (a live GLB `SubViewport` is not required this story). Every new control gets `AttachFieldTip` (copy the 4-line helper; UX-DR53, hover + keyboard focus).
- **Determinism/layer rules hold.** `PlayerProfile`, `LocalProfileSource`, `HeroProfileLoader` are Godot-free (`src/Core/Definitions/`, deterministic, Tier-1-testable, no `Dictionary` enumeration in the apply/mint path, no wall-clock/RNG in sim code, ascending-id iteration via `FoldOrder`). The overlay/phase are presentation (`src/UI/`, `src/Core/Bootstrap/Phases/`).
- **Save captures the hero's current init-eligible attributes through the manifest shape.** Save/Overwrite builds a `PlayerProfile` from a `(level, xp)` source resolved via `manifest.DeriveProfileShape()` (today `hero.level`/`hero.xp`); pre-3.13 that source is the hero's current state (a deployed profile's values, else the authored base). The shape-driven builder is the Tier-1-tested core; the UI supplies the live values.

**Block If:**
- (none — the story ACs, the epic's persistence-chain contract [3.9 = offline rail + picker + init-time apply; online rail is Epic 9; editor test-play is 3.10], and the 3.2/3.8 contracts fully determine the design.)

**Never:**
- Never fold `HeroStore` into `SimChecksum` or bump `SimChecksum.AlgoVersion` (9), `CanonicalModelHash.AlgoVersion` (3), or `StartStateHash.AlgoVersion` (1) — the per-tick `HeroStore` fold + its version bump is **Story 3.13**. 3.9 is init-time only, already covered by the existing `StartStateHash` walk. Do not edit `StartStateHash.cs`/`SimChecksum.cs`/`CanonicalModelHash.cs`.
- Never re-record the 18 SimChecksum replay goldens or `hero-start-state.golden.txt` (do not alter the `HeroStartStateScenario` fixture). Existing no-profile flows mint nothing → `HeroStore` stays empty → every golden/stamp is byte-identical.
- Never show the picker before the multiplayer Lobby (Epic 9 online rail) or before the editor Edit↔Play test-play (Story 3.10); never persist a mid-game snapshot.
- Never fold `EntityId` into any hash (it is the runtime link, producer-specific — `StartStateHash` already excludes it), and never store or fold XP as a float.
- Never block launch when persistence is enabled but no compatible/selected profile exists — "Play without a saved hero" always proceeds (minting nothing).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Deploy loads init state | `PlayerProfile{level=3, xp=Fixed}` deployed into a scenario placing that hero | `HeroProfileLoader` mints a `HeroStore` row (`HeroId=FNV(ProfileId)`, `Level=3`, `Xp`); `StartStateHash.Compute` (post-apply) folds it | No error |
| Deterministic re-load | Same profile into same scenario, applied twice | Byte-identical `StartStateHash` both times | No error |
| Level/XP changes the hash | Two profiles differing only in level or xp | Distinct `StartStateHash` values | No error |
| Incompatible profile | Profile whose `HeroDefId` is not a placed hero unit in the scenario | Nothing minted; `StartStateHash` equals the empty-store (no-profile) hash; picker greys the slot | Rejected (not deployable) |
| Persistence disabled | `ScenarioData.PersistenceManifest` null or `Enabled==false` | Picker does not appear; "Play Skirmish" toggles straight to Play as today; nothing minted | No error |
| Save into empty slot | Picker Save; no occupied target slot | `LocalProfileSource.Save` writes a new entry (new stable `ProfileId`) capturing the hero's `hero.level`/`hero.xp` per the manifest shape; disk JSON gains one profile | No error |
| Overwrite occupied slot | Save over an occupied slot | `ChimeraDialog` confirm (danger) → on confirm, the slot's profile is replaced (same `ProfileId`); on cancel, unchanged | Confirm-gated |
| Delete slot | Delete an occupied slot | `ChimeraDialog` confirm (danger) → on confirm, entry removed from disk; on cancel, unchanged | Confirm-gated |
| Multiple heroes per player | Several saved profiles | All listed as selectable slot cards (portrait + level + XP + signature + faction); single-select via `ListRowGroup` | No error |
| Play without a hero | Persistence enabled, player picks "Play without a saved hero" (or none compatible) | Launch proceeds to Play; nothing minted; hash = empty-store hash | No error |
| Corrupt/absent profile store | `user://hero_profiles` missing or unparseable JSON | `LoadAll` returns empty list (no throw), mirroring `SettingsManager.Load` fallback | Fail-soft (empty) |
| Full store / duplicate id on apply | `Mint` returns `-1` for a hero | That hero is skipped deterministically + logged; other heroes still mint; no partial-write divergence | Deterministic skip |

## Design Notes

- **D-1 — No hash edit, no version bump; ordering is the whole game.** `StartStateHash.Compute(model, heroes)` already folds `HeroId`/`Level`/`Xp.Raw` in `FoldOrder()` order (`StartStateHash.cs:54-73`). Folding real loaded state therefore needs ZERO change to the hash code — it needs the profile minted into `_host.Heroes` *before* `MainScene` computes the hash (`:~419`). Wire the mint after `ScenarioApplier.Apply` and before that line, or both peers hash content-only and the level/xp mismatch desyncs at tick 1 (the exact `StartCrystal` lesson this hash exists for). `SimChecksum`(9)/`CanonicalModelHash`(3)/`StartStateHash`(1) all stay put (`VersionStampConsistencyTests` enforces it); the per-tick `HeroStore` fold + its bump is Story 3.13.
- **D-2 — Deterministic `HeroId` = `FNV-64(ProfileId)`.** `HeroStore.cs:10-12` explicitly assigns the mint scheme to 3.9 and suggests "a deterministic hash of profile-id + save-slot." Hashing the stable persisted `ProfileId` gives producer-independent, reproducible ids (so re-load ⇒ byte-identical hash) that are unique because `ProfileId`s are unique. A `Mint` `-1` (astronomically-unlikely collision, or full store) is a deterministic skip+log on every peer — never a partial roster.
- **D-3 — Compatibility = manifest-enabled + a placed hero unit matching `HeroDefId`; apply is authoritative.** The picker greys a slot unless the scenario places a `ScenarioUnit` with `UnitId == profile.HeroDefId` and the manifest is `Enabled`. `LoadInto` mints only for spawned entities that are actually `IsHero` with the matching id, so a stray same-id non-hero can never receive hero state.
