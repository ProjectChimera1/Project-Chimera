## Intent

**Problem:** Post-9.3 the dedicated server is authoritative over merged ticks but NOT over four match-start/latency safety contracts the epic assigns to 9.4: (1) **input delay** — the P2P `DelayProposal` negotiation (`LockstepManager` Ping/Pong/`DelayMath`) is a **no-op through `DedicatedServer`** (its `HandlePacket` has no Ping/Pong/DelayProposal case, `DedicatedServer.cs:197-252`), so a server-mode match is frozen at `INPUT_DELAY = 4` with no adaptation; (2) **untrusted delay byte** — `DelayMath.AgreeDelay` deliberately does NOT re-clamp `theirDelayRaw` to `[2,12]`, a documented gap owned by this story (`DelayMath.cs:51-56`) that lets a forged proposal push the agreed delay past `BUFFER_SIZE=16` and corrupt the ring; (3) **PROTOCOL_VERSION** — written into Hello but never validated inbound (`TryReadHello` ignores the version bytes, `NetworkCommand.cs:654-661`; "the D3.8 gap", `VersionStampConsistencyTests.cs:209-213`); (4) **start-state agreement** — the server never checks that peers agree on start state (`HandleReady` counts readiness but ignores the Ready hash, `DedicatedServer.cs:257-299`), the wire carries only the 32-bit scenario hash (`MakeReady`/`TryReadReady`, `NetworkCommand.cs:669-690`), the 64-bit `StartStateHash` is compute-and-logged only (`MainScene.cs:502-505`; deferred-to-Epic-9 by `StartStateHash.cs:33-35`), and no `rulesetHash` over the effect-graph structural caps exists anywhere (`EffectCaps.cs:8` names them but computes no hash).

**Approach:** Make the server the single authority over input delay and make match start fail-closed on any start-state, protocol, or ruleset disagreement. (a) Add a Godot-free `DelayController` (`src/Multiplayer/Server/**`, Tier-1-globbed per `SimSources.props:66-69`) that collects per-slot RTT (server pings each client; client already echoes Ping→Pong at `LockstepManager.cs:533-536`), computes ONE dictated delay via the existing `DelayMath.ComputeTargetDelay`, and drives an all-N-ACK directive/commit state machine; `DedicatedServer` broadcasts a new server→client `DelayDirective (0x15)` and collects `DelayAck (0x43)`. (b) The client re-clamps the directive delay to `[MIN_DELAY, MAX_DELAY]` on receipt and applies it via the EXISTING `CommitDelayChange` apply-tick machinery; also re-clamp `theirDelayRaw` inside `AgreeDelay` (closes AC2c on the P2P path too). In server-dictated mode the client STOPS proposing/applying delay on its own (the load-bearing determinism invariant). (c) Bump `PROTOCOL_VERSION` 1→2 and validate it fail-closed both on the client's inbound Hello and on the server's inbound Ready. (d) Add a Godot-free `RulesetHash` FNV-64 over the `EffectCaps` structural caps. (e) Add a Godot-free `MatchAgreementHash` (FNV-64 over `{rulesetHash + initial-delay + faction-count + roster + StartStateHash}`), widen the Ready packet to carry it (64-bit) plus the protocol version, and gate match start on it — server-attested (`HandleReady` compares all slots, HALTs on disagreement) and, on the P2P path, via the widened `HandshakeGate`. `hash == 0` and version/hash mismatch are hard rejects.

## Boundaries & Constraints

**Always:** All determinism-critical and gate-decision logic lives in Godot-free types — `DelayController`/policy under `src/Multiplayer/Server/**`, `RulesetHash`/`MatchAgreementHash` under `src/Core/Definitions/` or `src/Effects/`, codecs in `NetworkCommand.cs`, math in `DelayMath.cs` — never inside `DedicatedServer`/`LockstepManager`/`LobbyUi`/`ServerTransport` (Godot-coupled, excluded from Tier-1). Slot identity stays transport-authoritative (RTT and ACK are keyed by the ENet peer→slot callback slot, never a packet byte). The dictated delay and every re-clamp result MUST stay within `[DelayMath.MIN_DELAY, DelayMath.MAX_DELAY]` (⊂ `[1, BUFFER_SIZE-1]`). In **server-dictated mode** the client applies delay changes ONLY from a `DelayDirective` — it must NOT send its own `DelayProposal` nor act on `MaybeProposeDelayChange` (a per-client unilateral change would make two clients pick different delays and desync); a single explicit mode flag on `LockstepManager` gates this. All clients receive the same directive with the same `applyAtTick` and re-clamp identically (clamp is deterministic), so they commit the same delay at the same tick — reuse `CommitDelayChange`'s existing empty-gap pre-seed (`LockstepManager.cs:672-696`). `MatchAgreementHash` folds `StartStateHash.Compute(model, heroes)` as its content component (a superset of the 32-bit scenario hash — it also catches hero/item-loadout mismatch) WITHOUT modifying `StartStateHash` itself. Fail-closed: any hash `== 0`, protocol-version mismatch, or per-slot hash disagreement blocks/HALTs the start (never fail-open).

**Block If:** Any pre-existing committed golden moves — `golden-scenario`, `golden-multifaction`, `golden-applier-scenario`, `golden-merged-n2`, `hero-start-state.golden.txt`, or the `SimChecksumCoverageGuardTest` pin — or `SimChecksum.AlgoVersion` (21) or `StartStateHash.AlgoVersion` (2) needs to change: this story is handshake/wire only and folds no new mutable sim array, so a moved sim golden means an unintended sim-path change — STOP, do not re-baseline. Block if the active player count / roster the client folds into `MatchAgreementHash` cannot be derived deterministically from the applied scenario model on the client at Ready time (it must be, since `CanonicalModelHash` already folds the player slots) — if it genuinely cannot, HALT rather than trust a server-supplied roster the client can't reproduce.

**Never:** Do NOT enable/verify >2 live players or raise `ServerTransport.MAX_PLAYERS` (N-shaping the delay/agreement code is in scope; live N>2 is Story 9.7/9.15). Do NOT implement disconnect-during-delay-change freeze/continue (Story 9.6) or drop-to-AI. Do NOT add anti-cheat: RTT inputs and client-reported values are trusted (trusted-friends EA) — the receipt re-clamp is the ONLY hardening. Do NOT change `StartStateHash.Compute`'s folded set or `AlgoVersion`, and do NOT fold delay/agreement/RTT into `SimChecksum`. Do NOT rip out the P2P `DelayProposal` path (it remains the LobbyUi 2-player behavior — only add the re-clamp to `AgreeDelay`).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Server RTT collect | server pings slot s, receives Pong | per-slot smoothed RTT (EWMA) updated in `DelayController` | stale/invalid Pong ignored |
| Dictate delay | new dictated delay ≠ current, all players present | server emits ONE `DelayDirective{delay, applyAtTick}` to all peers; ACK state reset | no directive while one is pending un-ACKed |
| Receipt re-clamp | client gets `DelayDirective` with delay byte d | applied delay = `Clamp(d, MIN_DELAY, MAX_DELAY)`; pending change scheduled at `applyAtTick`; `DelayAck` sent | out-of-range d clamped, not rejected |
| All-N-ACK | every player ACKed (delay, applyAtTick) | server logs commit; may issue the next directive | partial ACK → server keeps directive pending |
| P2P forged delay | `AgreeDelay(myDesired, 200)` | returns `max(myDesired, Clamp(200,2,12))` = `max(myDesired,12)` | never exceeds MAX_DELAY |
| Client self-propose (server mode) | server-dictated flag set, RTT changes | client does NOT send `DelayProposal` / schedule its own change | delay only mutates via directive |
| Protocol mismatch (Hello) | client reads server Hello with version ≠ PROTOCOL_VERSION | client blocks start (reason surfaced), does not proceed | fail-closed |
| Protocol mismatch (Ready) | server reads Ready with version ≠ PROTOCOL_VERSION | server broadcasts `Halt(ProtocolMismatch)`, does not StartGame | fail-closed |
| Ruleset hash | fold `EffectCaps` caps | deterministic non-zero 64-bit `RulesetHash`; changing any cap changes it | 0 → sentinel 1 |
| Start-state agree (server) | all slots' Ready hash equal & non-zero, versions match | StartGame broadcast at ShouldStart | any 0 / mismatch → `Halt(StartStateDisagreement)`, no start |
| Start-state agree (P2P) | `HandshakeGate.CheckStart(localHash, peerHash)` (64-bit) | null (allow) iff equal non-zero | 0 either side or mismatch → block reason |
| Ready wire round-trip | `MakeReady(version, hash64)` → `TryReadReady` | version + 64-bit hash read back byte-identical | short/undersized → false (fail-closed) |

**Acceptance Criteria:**
- Given a server-mode match, when RTT rises, then the server emits exactly one `DelayDirective` with a delay in `[2,12]` and an `applyAtTick`, collects a `DelayAck` from every player, and logs the commit; the client applies the clamped delay at `applyAtTick` via `CommitDelayChange` and, being `ServerDictatedDelay`, never sends its own `DelayProposal`.

## Design Notes

**The load-bearing determinism invariant (server-dictated vs client self-proposal).** Today the client's `MaybeProposeDelayChange` (fired from `HandlePong`) is inert in server mode only because `DedicatedServer` drops the client's Ping. Once the server pings clients (so it can measure RTT) the client's Pong-driven self-proposal path would re-activate and each client would schedule its OWN delay change from its OWN RTT — two clients pick different delays → they disagree on which buffer slot a command lands in → desync. Therefore `ServerDictatedDelay` MUST hard-gate `SendPing`/`MaybeProposeDelayChange` off; the ONLY delay mutation in server mode is a `DelayDirective`, which every client re-clamps identically and commits at the same `applyAtTick`. This is why the directive carries an explicit `applyAtTick` and reuses `CommitDelayChange`'s empty-gap pre-seed verbatim.

**Why fold `StartStateHash` (not the bare 32-bit scenario hash) as the content component.** `StartStateHash`'s own class doc (`StartStateHash.cs:33-35`) states its wiring into "the network Ready-packet + the server-attested multi-hash handshake is DEFERRED to Epic 9 / M5" — this story IS that wiring. `StartStateHash` is a strict superset of the scenario content hash (it folds the `CanonicalModelHash` seed PLUS heroes + items), so folding it catches hero/item-loadout mismatches the epic's bare "scenarioHash" would miss; wiring only the weaker 32-bit hash when the stronger 64-bit one was purpose-built to land here would be a regression. `MatchAgreementHash` USES its value and does not modify `StartStateHash` — so `hero-start-state.golden.txt` and `StartStateHash.AlgoVersion=2` stay put.

**No SimChecksum fold.** Delay, RTT, and the handshake hashes are latency/agreement concerns, never mutable mid-match sim arrays, so per the checksum-fold-timing rule nothing folds into `SimChecksum` — `AlgoVersion` stays 21 and every sim golden stays byte-identical. The only "stamp" that moves is `PROTOCOL_VERSION` (1→2), a deliberate coordinated wire bump (`VersionStampConsistencyTests`).

**Ready wire layout.** `type(1) + protocolVersion(2 LE) + matchAgreementHash(8 LE)` = 11 bytes. Server validates the version (→ `ProtocolMismatch` HALT) and collects the hash per slot (→ `StartStateDisagreement` HALT); P2P peers compare via the widened `HandshakeGate`. A short/undersized Ready reads as fail-closed (hash 0 / parse-false), routing into the existing block.
