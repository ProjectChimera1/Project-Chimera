## Story

As a **creator**,
I want **to author a passive ability — a while-alive aura, an on-hit rider, or a permanent/periodic self stat-modifier — by picking a trigger condition from a closed, validated set and composing its effect with the same effect vocabulary as active abilities, then have the simulation run it automatically (no player cast) every tick / on every landed hit / from spawn**,
so that **I can give a unit a continuously-running or condition-triggered effect without writing code, and the showcase factions' signature passives (Sanguine Furnace regen, aura buffs) actually run in a match — reusing every primitive Stories 2.1–2.5 already shipped.**

This story closes the **passive** side of the D1 effect engine. The **active** path is complete: 2.1 (effect vocabulary + executor), 2.2a/2.2b (ModifierSystem + ModifierStore with Persistent DoT/HoT), 2.3 (`AbilityDefinition` model + `Validated<T>` gate), 2.4a/2.4b (runtime cast spine + command-card UI), 2.5a/2.5b (the active-ability authoring editor). **What does not exist yet is any way to express or run an ability that is NOT player-cast** — there is no passive/trigger field on `AbilityDefinition`, no per-tick aura driver, no on-hit hook in combat, and no spawn-time auto-install. This story adds the **activation model** + the **sim runtime** that consumes it + the **editor mode** that authors it. It reuses the same `AbilityDefinition` JSON, the same `ModifierStore`, the same executor, and the same validate-gated save — **no new file format, no scripting escape hatch.**

## Acceptance Criteria

> **AC numbering note:** AC1/AC2/AC3 are the **three epic ACs verbatim** (epics.md:956-960). AC4 (determinism fence), AC5 (closed activation model — the "no scripting" guarantee), and AC6 (Godot-free testability + `/godot-verify`) are the project's standard re-asserted ACs. **PART A (2.6a)** owns the sim halves of AC1/AC2/AC3 + AC4 + the model half of AC5; **PART B (2.6b)** owns the authoring halves of AC1/AC2/AC3 + the editor half of AC5 + AC6's `/godot-verify`.

**AC1 — While-alive aura (FR-9; SIM = 2.6a, EDITOR = 2.6b).**
**Given** the Ability Editor passive mode **When** the creator authors a 'while-alive aura' passive (`SearchArea` allies in radius → `ApplyModifier` a stat buff) and attaches it to a unit **Then** **every tick** the owning unit grants the modifier to nearby allies and **removes it when they leave the radius or the unit dies** **And** the passive validates through the gate and runs **before `CombatSystem` reads `Effective*` stats**.
- *Mechanism (architecture `game-architecture.md:430`): "aura = a short Modifier re-applied each tick to units found via `SearchArea`." The driver re-applies a `StackRule.Refresh` modifier with a short duration each tick; a target that leaves the radius (or an owner that dies) simply stops being re-applied to, and the modifier expires on its own next tick. **No "remove" bookkeeping array is needed** — expiry-by-non-refresh is the mechanism, and it is what keeps the determinism fence clean (Decision #5).*
- *⚠ The naive "model the aura as a `Persistent(period_effect = SearchArea → ApplyModifier)`" is **blocked twice** and MUST NOT be used: `ModifierStore.RunEffect` passes `spatial: null` so a period `SearchArea` returns 0 targets (`ModifierStore.cs:469`), AND an install-leaf inside a Persistent phase is re-entrancy-unsupported and **rejected by `AbilityValidator`** (`AbilityValidator.cs:147-149`, the 2.3 AC5(b) rule). The aura is a **driver-level** per-tick pass, not a Persistent graph.*
- *✅ "+armor" RESOLVED (Decision #6 = Option B, Alec 2026-06-29): **build the real buffable armor stat.** Today `Modifier` has no armor delta (`Modifier.cs:43-90`), there is no `Effective*` armor stat, AND the combat formula has no `− armorValue` term (`DamageResolver` is `amount × matrix` only — the armor subtraction was never built, per the 2.1 as-built note). This story adds: `Modifier.ArmorDelta` (Fixed) + `UnitDefinition.armor` (authored) + a `BaseArmor`/`EffectiveArmor` per-entity pair (the 2.2a `Effective*` pattern) + the `− EffectiveArmor[target]` term in `DamageResolver` (floored at 0). The aura then grants `+armor` literally. **This is the source of the AC4 determinism FOLD** (`EffectiveArmor` folds into the checksum). Existing units default `BaseArmor = Fixed.Zero`, so the new `− 0` term leaves every existing combat outcome unchanged — the goldens move ONLY from the fold (a new all-zero field), never from the formula.*

**AC2 — On-hit rider (FR-9; SIM = 2.6a, EDITOR = 2.6b).**
**Given** a passive with an on-hit trigger condition (run effect when this unit's attack lands) **When** the unit deals an attack in a match **Then** the passive's effect graph **fires deterministically on the hit and not otherwise** **And** the trigger condition is **selected from the closed D1 condition set** and the editor offers **no scripting or free-text logic**.
- *This is the heaviest task. There is **no on-hit hook anywhere** in the combat/projectile path today (grep confirms zero `OnHit`/`AttackLanded`/`OnDamageDealt`), and the **attacker entity id is not even available at the hit**: `DamageContext` carries only `Killer` (a `Faction`, `DamageResolver.cs:12-33`) and `ProjectileStore.Owner` is `Faction[]` (`ProjectileStore.cs:24`). The rider needs (a) the attacker entity id threaded to the hit, (b) an `EffectExecutor` (+ `ModifierStore`) wired into the combat path, (c) a per-entity authored "on-hit ability index" SoA to know which graph to run.*
- *"Fires on the hit and not otherwise" is satisfied by hooking the **existing attack-resolution gate** (the `AttackCooldown` already decides when an attack lands, `CombatSystem.cs:457-459`) — **do NOT add a new per-entity on-hit counter** (that would force a determinism fold; Decision #5).*
- *Scope decision (Decision #7): **melee-first**. The melee hit point (`CombatSystem.cs:482`) has the attacker id in scope; ranged hits resolve later in `ProjectileSystem.ApplyHit` (`:89`) where the attacker id is currently lost. Default: ship melee on-hit in 2.6a, carve off ranged on-hit (needs `ProjectileStore.Spawn`/`Owner` to carry the attacker entity id) as a follow-up.*

**AC3 — Periodic / permanent self-passive (FR-9; SIM = 2.6a, EDITOR = 2.6b).**
**Given** a passive 'Furnace Trickle'-style continuous self-regen authored as a `Persistent(period_effect = Heal)` modifier **When** the owning unit is alive over several ticks **Then** its health regenerates by the configured `Fixed` amount per period **up to `MaxHealth`** **And** two identical runs produce **byte-identical golden checksums**.
- *The **runtime already exists**: `ModifierStore.InstallPersistent` (`:189`) + the period pulse in `Advance` (`:240-253`) + `HealEffect`'s `[0, EffectiveMaxHealth]` clamp (`HealEffect.cs:30`) all work. **The only missing piece is the spawn-time auto-install** — `ApplyUnitDefinition` installs no modifier today. This same install path also covers the "permanent stat modifier" passive (epic: "passive stat mods = a permanent `Modifier` on the owning entity") by installing an `ApplyModifier(duration_ticks < 0)` graph instead of a `Persistent`.*

**AC4 — Determinism FOLD (7→8) for the armor stat (PART A owns this).**
**Given** the **passive registration + the 3 drivers add no folded state** (they reuse `ModifierStore` v6, `Health`/`Energy`/`Effective*` v6, `AbilityCooldownTicks` v7, and register passives via **authored, not-folded** per-entity SoA — the `AbilityId` pattern) **but** the buffable armor stat (Decision #6) introduces **`EffectiveArmor` as new mutable-mid-match state** **When** the change is complete **Then** execute the **ONE intentional fold:** bump `SimChecksum.AlgoVersion` **7→8**, fold `EffectiveArmor[i].Raw` into `SimChecksum.Compute` (alongside the v6 `Effective*` block), **re-baseline ALL goldens once** (the 9 existing — `golden-scenario`, `golden-multifaction`, `golden-applier-scenario`, `same-tick-tie-break`, `command-vocabulary-scenario`, `formation-separation-scenario`, `modifier-scenario`, `ability-cast-scenario`, `ai-active-scenario` — plus the new `passive-*` goldens), and re-pin `SimChecksumCoverageGuardTest`'s known-state (`ExpectedV7Hash = 0xEB4B548E` → a freshly-computed `ExpectedV8Hash`). `SystemOrderTest.cs`/`ReplayRecorder.VERSION`(2)/`CanonicalModelHash.AlgoVersion`(2)/`PROTOCOL_VERSION`(1) stay **untouched**.
- *Existing combat outcomes are **unchanged** (`BaseArmor = Fixed.Zero` → `− 0`), so after the re-baseline a golden whose POSITION still differs (beyond the added all-zero `EffectiveArmor` field) = a leaked sim write (a passive system running on a non-passive scenario, or float in sim) → **fix the leak.** `BaseArmor` is authored (not folded, like `BaseAttackDamage`); only `EffectiveArmor` folds (like `EffectiveAttackDamage`).*
- *🚨 **Keep the fold to EXACTLY `EffectiveArmor`.** The passive DRIVERS must add **no** new mutable-mid-match counter: the aura uses **every-tick re-apply** of a short `Refresh` modifier (architecture `:430`), NOT a per-owner period timer; the on-hit uses the **existing `AttackCooldown` gate**, NOT a last-hit-tick counter; **melee-only** on-hit (Decision #7) avoids touching `ProjectileStore`. If a driver counter proves genuinely unavoidable, fold it in the **same** 7→8 bump (never two version bumps in one story). Per [[chimera-checksum-fold-timing-rule]], fold only what first goes mutable mid-match. State the final posture in the Dev Record.*

**AC5 — Closed, statically-validatable activation model; no scripting (MODEL = 2.6a, EDITOR = 2.6b).**
**Given** the passive activation is a **closed enum** (`active` | `aura` | `on_hit` | `while_alive`) on `AbilityDefinition`, deserialized through the existing closed-`kind` converter discipline **When** an ability is validated **Then** the `AbilityValidator` enforces the per-activation **shape rules** (below) with a **located error**, rejects any unknown activation string, and **no scripting / free-text / `customParams` payload is accepted** — the editor's activation selector offers **exactly** the closed set and nothing else.
- Shape rules (Task 1.3): `aura` ⇒ targeting `None`, effect root is a `SearchArea` whose child resolves to `ApplyModifier` (the per-tick grant); `on_hit` ⇒ targeting `None`, a non-empty rider graph; `while_alive` ⇒ targeting `Self`/`None`, the effect root is an `ApplyModifier` (permanent: `duration_ticks < 0`) **or** a `Persistent` (with ≥1 phase and `period_ticks > 0` when a `period_effect` is present — closes 2.5b deferred #1/#2 at the validator for passives); `active` ⇒ today's rules unchanged. **Passives carry no `cost_energy`/`cost_ore`/`cost_crystal`/`cooldown`** (validator rejects non-zero, or they are ignored — Decision #4).

**AC6 — Godot-free helpers Tier-1 covered; passive editor `/godot-verify`'d (EDITOR = 2.6b; sim Tier-1 = 2.6a).**
**Given** the sim runtime is pure C# (`src/Effects`, `src/Combat`, `src/Core`) and the editor is a Godot `Control`-tree **When** the story is implemented **Then** every new sim driver + the activation-model parse/validate is **Tier-1 xUnit covered (Godot-free)** with **gate teeth** (inject a violation → RED → revert), and the editor passive mode + the flag-combo checkbox UI are verified via **`/godot-verify`** (author each of the 3 passive types via controls → validate → Save & Reload → attach via faction JSON → observe the aura grant / on-hit fire / self-regen in a match).
