# Story 2.2b: D1 ModifierStore — SoA store with apply/stack/refresh/expire, DoT/HoT, Energy cost, determinism

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an engine developer,
I want a net-new SoA `ModifierStore` that installs, stacks, refreshes, and expires the first-class `Modifier` descriptor and the `PersistentEffect` time-axis (DoT/HoT) against the 2.2a effective-stat substrate, debits `Energy` with refuse-when-insufficient, clears an entity's modifier state on death/recycle, and folds its mutable state into `SimChecksum` (the one scheduled `AlgoVersion 5→6` re-baseline),
so that buffs, debuffs, auras, DoT/HoT and stat modifiers are expressible deterministically — the AR-9 primitive without which MOBA/TD/RPG content is unbuildable.

## Acceptance Criteria

**AC1 — DoT/HoT via `Persistent(periodEffect)` + Energy debit/refuse.** _(epic)_
**Given** a HoT installed via a `PersistentEffect` whose `PeriodEffect` is a `HealEffect` and a DoT whose `PeriodEffect` is a `DirectHpDeltaEffect`, each with `PeriodTicks`/`PeriodCount` **When** the period elapses over several `ModifierSystem` ticks **Then** the host entity's `Health` changes by the expected independently-derived `Fixed` amount on exactly each period boundary (not every tick), clamped into `[0, EffectiveMaxHealth]`, and the instance **expires after its configured lifetime** (no further pulses) **And** `ModifierStore` can debit a `Fixed` cost from `EntityWorld.Energy[id]` via `TryDebitEnergy`, succeeding (and subtracting) only when `Energy[id] >= cost` and **refusing without mutating `Energy`** when insufficient.

**AC2 — apply / stack / refresh / expire determinism, store folded.** _(epic)_
**Given** two runs of a fixed scenario that applies, stacks (`StackRule.Stack` up to `MaxStacks`), refreshes (`StackRule.Refresh`), ignores (`StackRule.Ignore`), and expires same-id and distinct-id modifiers across ticks **When** a golden `SimChecksum` is computed at matching ticks in both runs **Then** the two checksum sequences are **byte-identical** **And** `ModifierStore` mutable state participates in the determinism path — folded into `SimChecksum`, no `float`, iterated in ascending owner-entity-id then ascending slot order.

**AC3 — the single scheduled `SimChecksum` fold (AlgoVersion 5→6), re-baseline once.** _(story-added — the one intentional checksum bump [[chimera-checksum-fold-timing-rule]])_
**Given** the 2.2a effective-stat arrays now mutate mid-match (a modifier changes `Effective*`; an ability debits `Energy`) and the new `ModifierStore` state **When** this story lands **Then** `SimChecksum.Compute` folds `EffectiveAttackDamage`/`EffectiveMaxHealth`/`EffectiveMoveSpeed`/`Energy` (in the entity loop) **and** the `ModifierStore` per-instance state (ascending owner-id then slot), `SimChecksum.AlgoVersion` is bumped **5→6**, the pinned known-state hash in `SimChecksumCoverageGuardTest` is re-recorded **once** from a green run, `VersionStampConsistencyTests`' `ExpectedSimChecksumAlgoVersion` is moved to 6, and **all 7 existing `*.golden.txt` are re-baselined exactly once** (no hand-editing) **And** the coverage guard is extended to prove each newly-folded field actually moves the hash (teeth), and `Base*` arrays remain **unfolded** (authored, in-tick-immutable).

**AC4 — recycle safety: `ClearEntity` on destroy + teeth.** _(story-added — closes the 2.2a SoA-recycle carve-off; the 2.2a-review prescription)_
**Given** an entity carrying active modifiers (nonzero `ModifierStore` slots **and** a nonzero `ModifierSystem` stat-bonus accumulator) **When** the entity is destroyed and its slot is recycled by a later `EntityWorld.Create` **Then** the recycled entity carries **no residual** modifier instance and **no residual** stat bonus — `ModifierStore` and the `ModifierSystem` accumulators/dirty flag for that id are cleared on `Destroy` (via a single `EntityWorld` destroy hook), proven by a Tier-1 guard that goes **RED** if either clear is removed **And** the cleared state is reflected in the checksum (a recycled-then-rebuilt entity hashes identically to a freshly-built one).

**AC5 — stat-modifier apply/remove through the 2.2a `AccumulateBonus` seam; MaxHealth + negative-clamp policy.** _(story-added — the buff/debuff correctness the store exists for, AR-9)_
**Given** a `Modifier` with `AttackDamageDelta`/`MaxHealthDelta`/`MoveSpeedDelta` and `StatusFlags` **When** `ModifierStore.Apply` installs it and `ModifierStore` later removes it (expiry or explicit) **Then** the install adds the deltas via `ModifierSystem.AccumulateBonus(+delta)` so `EffectiveAttackDamage`/`EffectiveMaxHealth`/`EffectiveMoveSpeed` recompute to `Base + Σ active deltas` the **same tick** (Modifier@3 before Combat@4), removal subtracts them (`−delta`) reverting to `Base`, and the status flags are set on apply and cleared on remove **And** the recompute floors each `Effective*` at `Fixed.Zero` (a debuff can never drive damage/speed negative), and on any `MaxHealthDelta` change the host's current `Health` is clamped down to the new `EffectiveMaxHealth` (a removed +MaxHealth buff never leaves phantom HP) — but is **not** healed up on apply (no free heal).

_Covers: FR-12, AR-9, AR-8, NFR-4. Depends on: 2.2a (the `Base*`/`Effective*`/`Energy` substrate + the `ModifierSystem` dirty-flag recompute + the `AccumulateBonus` seam — all green), 2.1 (the `Modifier` descriptor, `ApplyModifierEffect`/`PersistentEffect` types, `EffectExecutor` — all green)._

- [ ] **Task 2 — Apply / stack / refresh / ignore / expire + the `AccumulateBonus` wiring + clamps (AC2, AC5)**
  - [ ] 2.1 `public void Apply(int targetId, Modifier mod, int casterId, Faction casterFaction)`: guard `world.IsAlive(targetId)` + id-bounds (no throw on a dead/stale id — return). Resolve stacking by scanning the target's active slots for a same-`mod.Id` instance:
    - **No existing instance** → install into the first free slot (`_count[targetId] < MaxModifiersPerEntity`; if full, **refuse deterministically** — drop the apply, optionally log; never overflow): set the slot fields, `_stackCount = 1`, init `_remainingTicks`/`_ticksUntilPeriod`/`_periodsRemaining` from `mod` (see Dev Notes §Lifetime), then `system.AccumulateBonus(targetId, mod.AttackDamageDelta, mod.MaxHealthDelta, mod.MoveSpeedDelta)` and OR-in `mod.Status` (Task 2.4) and apply the MaxHealth clamp (Task 2.5).
    - **`StackRule.Refresh`** → reset the existing slot's `_remainingTicks` to `mod.DurationTicks` (and `_ticksUntilPeriod`/`_periodsRemaining` per Dev Notes); **no second bonus, no second stack** (the enum doc: "resets the existing instance's duration; no second stack").
    - **`StackRule.Stack`** → if `_stackCount < mod.MaxStacks`: increment `_stackCount`, `AccumulateBonus(+deltas)` **again** (each stack re-adds its deltas), refresh the shared `_remainingTicks` (Dev Notes §Stack-duration: single-slot shared duration, all stacks expire together — the simple deterministic model); at `MaxStacks`, behave as Refresh (refresh duration only). Re-OR the status (idempotent).
    - **`StackRule.Ignore`** → an active same-id instance makes the re-apply a **no-op** (no refresh, no stack — the enum doc: "ignored while an instance is active").
  - [ ] 2.2 `Remove` / expiry (`private void RemoveSlot(int targetId, int slot)`): subtract the **full** stat contribution — `AccumulateBonus(targetId, −delta * _stackCount[...])` (a stacked modifier removes ALL its stacks' deltas at once); clear the status flags it imposed **only if no other active slot imposes them** (recompute the union of remaining slots' `mod.Status`, write that — never blindly clear a flag another modifier still holds); run `ExpireEffect` if the descriptor is a `PersistentEffect` with one (Task 3); compact the slot out (swap-with-last within the entity's slots to keep `[0, _count)` dense, **then** decrement `_count` — preserve ascending determinism by re-sorting is NOT needed since fold reads `[0, _count)` and a swap-compact is deterministic given identical apply/remove order across peers); mark the entity dirty so the recompute reverts `Effective*`.

  - [ ] 2.4 **Negative-clamp policy in the recompute (AC5).** Extend `ModifierSystem.Tick`'s recompute (2.2a `ModifierSystem.cs:51-53`) to floor each effective stat at `Fixed.Zero`: `EffectiveAttackDamage[i] = Fixed.Max(Fixed.Zero, BaseAttackDamage[i] + _flatAttackDamageBonus[i]);` (and the same for MaxHealth, MoveSpeed). A debuff can never drive damage/speed/maxhealth negative (which would heal via `DamageResolver`, reverse movement, or invert the Health clamp).   - [ ] 2.5 **MaxHealth-buff Health semantics (AC5).** On any apply/remove that changes `MaxHealthDelta` for a target, after `AccumulateBonus`, **recompute that entity's `EffectiveMaxHealth` eagerly** (or read it post-Tick) and clamp `world.Health[targetId] = Fixed.Min(world.Health[targetId], EffectiveMaxHealth[targetId])`. **Apply raises the ceiling but does NOT heal current Health** (no free heal); **remove clamps Health down** to the new ceiling (no phantom HP). ## Dev Notes

### What this story is

The **AR-9 ModifierStore** — the store of active, timed modifier *instances* that DRIVES the 2.2a effective-stat pipeline. 2.2a built the substrate (`Base*`/`Effective*`/`Energy` arrays + the dirty-flag `ModifierSystem` recompute + the `AccumulateBonus(±delta)` seam, all a no-op because nothing applied a modifier). 2.2b builds the thing that applies them: install/stack/refresh/expire the first-class `Modifier` descriptor, run `PersistentEffect` time-axis DoT/HoT, debit `Energy`, clear on recycle, and fold the now-mutable state into the checksum. **This is the primitive without which buffs/auras/DoT/MOBA/TD/RPG content cannot exist.**

> _Architecture AR-9 (game-architecture.md:427-434):_ "Modifier object spec (SoA-attached): { id, durationTicks, stackRule (Refresh|Stack|Ignore), maxStacks, Fixed statDeltas, statusFlags bitmask, optional periodicEffect + periodTicks }. Buff = positive deltas; debuff = negative; aura = a short Modifier re-applied each tick via SearchArea; DoT = periodicEffect = Damage. Effective stat = base + Σ deltas, dirty-flagged, resolved deterministically by modifierId + stackRule in ascending entity-ID order. Requires a new SoA modifier store, a ModifierSystem (ISimSystem), and Energy/Mana SoA arrays."

### 🔑 Determinism posture — 2.2b DOES fold (read this twice; it is the OPPOSITE of 2.1/2.2a)

Stories 2.1 and 2.2a deliberately did **not** fold (their new arrays were dormant — `Effective==Base`, `Energy==0`, no modifiers). **2.2b is the one scheduled re-baseline** ([[chimera-checksum-fold-timing-rule]]): the moment `ModifierStore` MUTATES an `Effective*` or DEBITS `Energy`, those become peer-divergent sim truth and MUST fold.

- **Fold:** `EffectiveAttackDamage`/`EffectiveMaxHealth`/`EffectiveMoveSpeed`/`Energy` (entity loop) + the `ModifierStore` per-instance numeric state (ascending owner-id then slot) + `StatusFlagsOf` (if Decision #2 routes it through EntityWorld). **AlgoVersion 5→6. Re-baseline all 7 goldens ONCE + add the new modifier golden. Re-pin the known-state hash + the version-stamp guard.**
- **Do NOT fold:** `Base*` (authored, in-tick-immutable — exactly like the pre-2.2a `AttackDamage`/`MaxHealth`/`Speed` were never folded); the `ModifierSystem._dirty`/`_flat*Bonus` accumulators (transient recompute optimisation — the recompute is idempotent and they are a deterministic function of the folded modifier set, so peer dirty-timing cannot diverge `Effective`; **keep them private + unhashed forever**, per the 2.2a class doc); the `Modifier`/`PersistentEffect` descriptor references and `_casterId`/`_casterFaction` (authored/peer-identical by construction — like a `UnitDefinition` reference).

But the record path refuses to write if two in-process runs diverge; if a re-record fails that guard, you have a real nondeterminism bug (a `float`, a `Dictionary` enumeration, a non-ascending iteration, a stale recycle) — fix the bug, do not force the record.

### The store ↔ system ↔ executor wiring (the index-3 orchestration)

```
EntityWorld.Destroy(id) ──fires──▶ OnDestroy(id) ──▶ ModifierStore.ClearEntity(id) ──▶ ModifierSystem.ClearEntity(id)
                                                         (revert bonuses, zero slots)      (zero _flat*Bonus, _dirty)

ModifierSystem.Tick(world, dt):
   _store?.Advance(world, dt);     // periods fire, expiries RemoveSlot → AccumulateBonus(−delta), all ascending-id
   <existing 2.2a dirty-flag recompute, now Zero-floored>   // Effective = max(0, Base + Σbonus); combat@4 reads it this tick

ApplyModifierEffect.Apply(ctx):  ctx.ModifierStore!.Apply(ctx.PrimaryTargetId, Modifier, ctx.CasterId, ctx.CasterFaction)
```

**Why `ModifierSystem` drives the store (not a separate ISimSystem):** the architecture reserves exactly ONE slot at tick index 3 (AR-9). Splitting apply-recompute across two systems would either reorder the contract or lag a tick. `ModifierSystem.Tick` = `Advance(store)` then `recompute` keeps everything before `CombatSystem@4` in one slot. `SystemOrderTest` stays at 10 systems (do NOT add a system — the store is driven by the existing index-3 system, like the executor is a helper not a system).

### Re-entrancy: the store owns a DEDICATED executor

The store runs period/initial effects via `_executor.Run(...)`. The `EffectExecutor` has a single pre-allocated work-stack + `LastPeakStackDepth` — running a graph **re-entrantly on the same instance clobbers the stack**. So the store's `_executor` MUST be a distinct instance from any graph-running executor (the one 2.4's ability-cast will own). In 2.2b there is no graph-running caller yet (the store is driven directly), so re-entrancy cannot occur today — but build the dedicated-executor discipline in now so 2.4 inherits it. Period effects are direct-target (`spatial: null`), so no `SearchArea` nesting.

### Lifetime, period, and permanent semantics

- `Modifier.DurationTicks`: `0` = instantaneous (apply the deltas/period-zero pulse and expire same tick — or treat as one-shot per the descriptor doc), `> 0` = `_remainingTicks` countdown, `< 0` = **permanent** (sentinel — never decrement; only removed explicitly or on recycle). Pick a clear sentinel (e.g. `_remainingTicks = int.MinValue` for permanent) and document it; the fold mixes the sentinel deterministically.
- `Modifier.PeriodEffect`/`PeriodTicks`: a modifier MAY carry its own period (DoT-buff). `_ticksUntilPeriod` inits to `PeriodTicks`; fire on 0, reset. Bound total periods by `EffectCaps.MaxPersistentPeriods` (256) — a modifier whose duration/period would schedule more is clamped (named-cap, CHM0004-clean).
- `PersistentEffect` (the AC1 DoT/HoT path): `InitialEffect` runs on install, `PeriodEffect` every `PeriodTicks` for `PeriodCount` periods (≤ `MaxPersistentPeriods`), `ExpireEffect` on the final period. A pure `PersistentEffect` instance carries no stat deltas/status (deltas Zero) — it is the time-axis-only entry. **Unify** Modifier-instances and Persistent-instances in one slot model: the slot holds whichever descriptor installed it; the period/expiry logic reads `PeriodEffect`/`ExpireEffect` from either source (the `Modifier` also exposes `PeriodEffect`/`PeriodTicks`).

### Stacking — the enum doc IS the spec (do not re-derive)

`StackRule` (`Modifier.cs:7-15`) already specifies the semantics; implement them verbatim:
- **Refresh** (0): "Re-applying resets the existing instance's duration; no second stack." → one slot, reset `_remainingTicks`, bonus stays 1×.
- **Stack** (1): "Re-applying adds an independent stack, up to `MaxStacks`." → 2.2b model = a single slot with `_stackCount`, each stack re-adds `+deltas`, **shared duration refreshed**, **all stacks expire together** (the simple deterministic model; independent per-stack expiry timers are a deferred refinement — flag in `deferred-work.md`). At `MaxStacks`, a further apply refreshes duration only.
- **Ignore** (2): "Re-applying is ignored while an instance is active." → no-op (duration NOT reset).

### Negative-clamp + MaxHealth semantics (the 2.2a-review prescriptions, AC5)

- **Negative floor (defer #2):** `CombatSystem`'s non-combatant gate is `EffectiveAttackDamage == Fixed.Zero` (not `<= 0`); a negative effective damage would NOT be skipped and would flow into `DamageResolver.Apply` → **heal** the target. `MovementSystem` has no speed floor (negative = reverse). So the recompute MUST floor each `Effective*` at `Fixed.Zero` (Task 2.4). "Can't attack" is modeled by `StatusFlags.Disarmed` (a later story reads it), NOT by debuffing damage below zero.
- **MaxHealth (Health adjustment is the open fork, AC5):** the Heal/DirectHpDelta clamp already reads `EffectiveMaxHealth` (2.2a), so the ceiling is correct. The open decision is the on-apply/on-remove Health adjustment. **Recommended (Decision #3):** apply RAISES the ceiling without healing (no free heal); remove CLAMPS `Health` down to the new ceiling (`Fixed.Clamp(h, Zero, EffectiveMaxHealth)` would become `max<min` if a removed +MaxHealth buff left `Health > EffectiveMaxHealth` — clamping down prevents that and the phantom-HP bug).

## Open Decisions for Alec (defaults baked in; confirm or override)

> Per the create-story protocol, the story is written end-to-end with recommended defaults so it is immediately implementable. Three forks genuinely benefit from your call; the rest are resolved-by-default with rationale (override any if you disagree).

**Decision #1 — Stacking sub-model (RESOLVED-by-default; the enum doc already specifies the rules).** `Refresh`/`Stack`/`Ignore` follow the `StackRule` enum docs verbatim. The one sub-choice: a `Stack` modifier uses a **single slot with a `_stackCount`, shared duration, all stacks expiring together** (simple + deterministic + foldable). Independent per-stack expiry timers are deferred. _Default: shared-duration stacks. Override if a mechanic needs per-stack timers in 1.0._

**Decision #2 — ModifierStore storage + checksum-fold mechanism (NEEDS YOUR CALL).**
- **Option B (recommended, baked in):** a net-new **self-contained SoA `ModifierStore`** in `src/Effects` (its own slot arrays), folded via a new `SimChecksum.Compute(..., ModifierStore)` parameter (~12 mechanical call-site updates); `StatusFlagsOf` lives on `EntityWorld` (folds via `world`); recycle-safe via the `OnDestroy` hook + `ClearEntity` + a dedicated guard test. **Pro:** matches the architecture's literal "net-new SoA ModifierStore" (`ModifierStore.cs` named at `:1629`) + the 2.2a-review's "add `ClearEntity` + a new guard" prescription; sets the fold-via-param precedent HeroStore (3.2) and DslVarTable (Epic 7) follow (`:1603` groups them).
- **Option A (lighter touch):** the foldable modifier **slot numerics live on `EntityWorld`** (fold via `world` — **no `Compute` signature change**; reset by `Create` — recycle-safe for free; coverage-guard-native), with `ModifierStore` as a thin logic class holding only the descriptor refs + apply/stack/expire logic. **Pro:** zero Compute-signature churn, fewer moving parts. **Con:** reinterprets "SoA store" as "slots-in-EntityWorld + logic class" (looser fit to the architecture/title) and grows `EntityWorld` by ~6 arrays.
- _Recommendation: **B** (architecture- and review-faithful; the churn is mechanical). Flip to **A** if you want to minimize the checksum-call-site blast radius and EntityWorld is the home you prefer for foldable per-entity state._

**Decision #3 — MaxHealth-buff Health semantics (NEEDS YOUR CALL; baked default below).** On a +MaxHealthDelta apply: **raise the ceiling, do NOT heal** current Health (no free heal). On remove: **clamp Health down** to the new `EffectiveMaxHealth` (no phantom HP). _Default: raise-no-heal / remove-clamp-down. Override to "heal proportionally on apply" if you want +MaxHealth buffs to feel like a heal (WC3 Roar does not heal; many MOBA HP buffs do)._

**Decision #4 — Energy regen (RESOLVED-by-default = OUT).** Ship only `TryDebitEnergy` + refuse-when-insufficient. The regen model is architecture-deferred (`:2526`) and there is no authored `MaxEnergy` and no ability to spend on until 2.3/2.4. _Default: no regen in 2.2b. Override if you want a flat per-tick `Fixed` regen now._

**Decision #5 — Negative-stat floor (RESOLVED-by-default = floor at Zero).** The recompute floors each `Effective*` at `Fixed.Zero` so a debuff can't heal/reverse via the `==Zero` combat gate. "Can't attack" is `StatusFlags.Disarmed` (read by a later story), not negative damage. _Default: Zero-floor. Low-risk; override only if you want signed effective stats (not recommended)._
