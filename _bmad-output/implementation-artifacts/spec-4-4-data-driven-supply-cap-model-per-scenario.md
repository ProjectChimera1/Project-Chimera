## Intent

**Problem:** The population/supply cap is entirely hardcoded: `ResourceStore.STARTING_SUPPLY_CAP = 10` is a compile-time constant applied unconditionally to every faction, every tick, by `BuildingSystem.RecalculateSupplyCaps()`. There is no scenario-level starting cap, no optional hard ceiling, and no way to disable the supply gate. (Per-building bonus is already data-driven via `BuildingDefinition.SupplyBonus`, Story 4.1 — not in scope here.)

**Approach:** Add an authored, nullable `ScenarioData.Supply` block (`SupplyConfig`: `starting_cap`, `hard_ceiling`, `enabled`) following the exact `ScenarioData.Resources`/`RevivalRule` precedent: null ⇒ today's default exactly. `ScenarioApplier.Apply` resolves it into new `ResourceStore` instance state (mirroring `RevivalRuntime.Configure(s?.RevivalRule)`'s unconditional-call idiom) that `BuildingSystem.RecalculateSupplyCaps` reads as its per-tick base/ceiling, and `ResourceStore.HasSupply` reads as its enable gate. Because `Supply` is sim-affecting (folds into the already-folded `SupplyCap`/`SupplyUsed` and gates `TrainUnit`), it must also be folded into `CanonicalModelHash` — the lobby mismatch-handshake hash — mirroring the `StartCrystal` precedent (Story 2.9b follow-up, `AlgoVersion` 2→3) that exists specifically so a sim-affecting field mismatch is rejected at the lobby handshake instead of desyncing in-sim from tick 1.

## Boundaries & Constraints

**Always:** `SupplyConfig.StartingCap` (int, default 10, mirrors `ResourceStore.STARTING_SUPPLY_CAP`), `HardCeiling` (`int?`, null = uncapped), `Enabled` (bool, default true). `ScenarioData.Supply` is `SupplyConfig?`, JSON `"supply"`, `[JsonIgnore(WhenWritingNull)]` — identical shape convention to `Resources`/`RevivalRule`/`PersistenceManifest`. `ResourceStore` gains instance properties `StartingSupplyCap` (default `STARTING_SUPPLY_CAP`), `SupplyHardCeiling` (`int?`, default null), `SupplyGatingEnabled` (default true), and `ConfigureSupply(SupplyConfig? config)` that resolves all three from `config` (or compile defaults when `config` is null) — called unconditionally from `ScenarioApplier.Apply` right after the existing `_host.RevivalRuntime.Configure(s?.RevivalRule)` line, as `_host.Resources.ConfigureSupply(s?.Supply)`. `ResourceStore.Clear()` resets all three to compile defaults (same pattern as its existing `_startingOre` reseed) so every `ClearForReset → Apply` cycle reproduces a fresh load byte-for-byte — no scenario's config may leak into the next. `BuildingSystem.RecalculateSupplyCaps` seeds each faction's `SupplyCap` from `_resources.StartingSupplyCap` (not the constant), then after adding building bonuses, clamps to `_resources.SupplyHardCeiling` when set. `ResourceStore.HasSupply` returns `true` unconditionally when `!SupplyGatingEnabled`, otherwise unchanged. `SupplyCap`/`SupplyUsed` arrays, their `SimChecksum` fold, and `SimChecksum.AlgoVersion` are untouched — the config only changes what feeds the already-folded arrays, so omitting `supply` must leave every golden checksum byte-identical. Separately, `CanonicalModelHash.Compute` (`godot/src/Core/Definitions/CanonicalModelHash.cs`) must fold `Supply`'s RESOLVED values (`m.Supply?.StartingCap ?? ResourceStore.STARTING_SUPPLY_CAP`, `m.Supply?.HardCeiling ?? -1` — mirrors `MixStr`'s existing "null folds as -1" convention, safe since `HardCeiling` is validated `>= 0`, and `m.Supply?.Enabled ?? true` as `1`/`0`) as three `MixInt` calls placed right after the existing `TerrainRef` mix and before the `PlayerSlots` loop — folding the resolved value, not the raw nullable field, so an omitted `supply` block and an explicitly-authored default hash identically (mirrors `StartStateHash`'s `model.InventorySlotCount ?? HeroStore.INVENTORY_SLOTS` precedent exactly). This requires bumping `CanonicalModelHash.AlgoVersion` from 3 to 4 (its own doc-commented versioning convention: "mixed FIRST, so a version bump moves the value even with no field change") and updating its doc comment. `StartStateHash.AlgoVersion` stays at 2 unchanged — it seeds from `CanonicalModelHash.Compute` so it inherits the new fold transitively; per its own doc comment it only bumps when ITS OWN folded fields/order change, which they do not here. This `CanonicalModelHash.AlgoVersion` bump is a DIFFERENT versioning system from `SimChecksum.AlgoVersion` (unrelated file, unrelated tests, unrelated `.golden.txt` fixtures) — it intentionally moves every existing `CanonicalModelHashTests`/`StartStateHashTests` pinned-hash test (both files reconstruct the expected byte stream independently rather than pinning a magic number, so update the reconstruction, not a literal). This does NOT violate the "byte-identical golden checksum" constraint above, which is scoped solely to `SimChecksum`/`.golden.txt`.

**Block If:** N/A — scoped to fully-specified files; both open design questions (hard-ceiling-vs-disabled interaction, config-resolution idiom) are resolved in Design Notes.

**Never:** Do not restructure `SupplyCap`/`SupplyUsed` storage or their `SimChecksum` fold, and do not bump `SimChecksum.AlgoVersion` (the `CanonicalModelHash.AlgoVersion` 3→4 bump required above is a separate system and IS required — see Always). Do not touch `BuildingDefinition.SupplyBonus` or its wiring (Story 4.1, already complete). Do not push a `CombatEventType.OrderDenied` or any new event on a supply-blocked `TrainUnit` call — that UI-feedback gap is pre-existing and out of scope; the silent `false` return stays unchanged. Do not gate `hard_ceiling`'s clamp on `enabled` — the ceiling shapes `SupplyCap` regardless of whether the gate enforces it (see Design Notes). Do not modify the literal-`10`-encoding assertions in `SimResetTests.cs`, `SimChecksumCoverageGuardTest.cs`, or the `BuildingStore*Tests.cs`/`BuildingDefinitionValidatorTests.cs` files — they must keep passing unmodified, run as regression proof that omitted config changes nothing.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Omitted `supply` (all existing content) | No `"supply"` key | `StartingSupplyCap=10`, `HardCeiling=null`, `Enabled=true`; every golden checksum byte-identical | No error expected |
| Authored starting cap only | `"supply":{"starting_cap":30}` | `SupplyCap` starts at 30 + building bonuses per faction, uncapped above | No error expected |
| Hard ceiling below building-bonus total | `"supply":{"starting_cap":10,"hard_ceiling":15}` with buildings pushing cap to 40 | `SupplyCap` clamped to 15 every tick; `TrainUnit` blocks once `SupplyUsed` reaches 15 | No error expected |
| Gating disabled | `"supply":{"enabled":false}` | `TrainUnit` never blocked on supply even when `SupplyUsed >= SupplyCap`; `SupplyCap`/`SupplyUsed` still computed, displayed, and folded | No error expected |
| `hard_ceiling` below `starting_cap` | `"supply":{"starting_cap":20,"hard_ceiling":5}` | `ScenarioValidator.Validate` fails closed | Located error naming the scenario id and both values |
| Out-of-range amount | `"supply":{"starting_cap":-1}` or `>= 32768` | `ScenarioValidator.Validate` fails closed | Located error naming the scenario id and field |

**Acceptance Criteria:**
- Given a scenario omitting `supply`, when applied and ticked, then `SimChecksum.AlgoVersion` and every existing golden checksum file remain byte-identical to the pre-story baseline.
- Given a scenario authoring `hard_ceiling`, when building bonuses would otherwise push a faction's `SupplyCap` above it, then `SupplyCap` never exceeds the ceiling on any tick, and `TrainUnit` blocks once `SupplyUsed` reaches it.
- Given a scenario authoring `enabled:false`, when a faction's `SupplyUsed` is at or above its computed `SupplyCap`, then `TrainUnit` still succeeds, while `SupplyUsed`/`SupplyCap` continue to be tracked and folded into the checksum identically to the enabled case.
- Given the Edit→Play reset (`ClearForReset` then re-`Apply`), when the same scenario is re-applied, then `StartingSupplyCap`/`SupplyHardCeiling`/`SupplyGatingEnabled` and the resulting `SupplyCap` are byte-identical to a fresh load of that scenario.
- Given two scenario models differing ONLY in `Supply` (e.g. one has `hard_ceiling:50`, the other omits it), when `CanonicalModelHash.Compute` runs on each, then the two hashes differ; given `Supply = null` vs. an explicitly-authored all-default `SupplyConfig`, then the two hashes are equal.

## Design Notes

**Why `ConfigureSupply` is called unconditionally, not `if (s.Supply != null)`:** Follows the same line's existing precedent, `_host.RevivalRuntime.Configure(s?.RevivalRule)` — the resolver, not the call site, owns the null-means-default logic. Keeps `ScenarioApplier.Apply` free of a growing pile of per-feature null checks as more scenario-level config blocks are added.

**Why `hard_ceiling` clamps `SupplyCap` even when `enabled:false`:** The ceiling is a shape of the cap value itself (what the HUD and AI headroom scoring read), independent of whether the gate blocks training. Treating them as orthogonal avoids a hidden coupling where toggling `enabled` silently changes the displayed cap too.

**Why config lives on `ResourceStore`, not a new store:** `SupplyCap`/`SupplyUsed` already live there and are already checksum-folded; adding three resolved-config properties beside them (mirroring the existing `_startingOre` ctor-param/`Clear()`-reseed idiom) needs no new store, no new checksum fold, and keeps `BuildingSystem.RecalculateSupplyCaps` — the sole per-tick writer of `SupplyCap` — a single-file change.

**Why `CanonicalModelHash` folds the RESOLVED value, not the raw `Supply` field:** Folding `m.Supply` directly (e.g. hashing "is it null") would make an omitted block and an explicitly-authored `{starting_cap:10,hard_ceiling:null,enabled:true}` block hash DIFFERENTLY even though they resolve to identical runtime state — a false-positive lobby mismatch. Folding the resolved value (mirroring `StartStateHash`'s `InventorySlotCount ?? HeroStore.INVENTORY_SLOTS`) makes the hash track runtime-observable state, not authoring syntax.
