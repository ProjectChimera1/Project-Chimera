## Intent

**Problem:** A creator has no way to declare *which* hero progression carries between their custom games. Story 3.2 gave heroes a stable cross-match identity (`HeroId`) and Story 3.7 made heroes authorable, but there is no per-scenario contract saying "Level and XP persist; nothing mid-game does," and no way to disable persistence per scenario. Without it, Story 3.9's offline Save/Load rail has no shape to load and no gate to reject a mid-game-snapshot cheat. AR-12 ("one PlayerProfile + PersistenceManifest through the validate gate") is unreachable.

**Approach:** **Authoring + validation + persistence only** (the load/apply rail is Story 3.9). (1) A closed Godot-free attribute catalog `PersistableAttributes` (mirroring `HeroLevelingPresets`) enumerating the init-time-eligible attributes that actually exist today (`hero.level`, `hero.xp`) plus a known-ineligible set of mid-game keys for specific fail-closed rejection. (2) A net-new nullable `PersistenceManifest` POCO stored omitted-when-null on `ScenarioData` (JSON `persistence_manifest`), holding an `enabled` toggle + selected attribute keys, with a pure `DeriveProfileShape()` yielding the `PlayerProfileShape` that Story 3.9 will fill. (3) A standalone `PersistenceManifestValidator` (multi-error located-list, mirroring `UnitDefinitionValidator` — NO `Validated<T>` mint) whose rule core is also called first-fail from `ScenarioValidator.Validate` so the manifest truly passes the D3 gate. (4) A new `PersistenceManifestPanel` editor (a checklist of eligible attributes + a master `ChimeraSwitch`, composed from the 3.1 kit) mounted as an `ISetupPhase` + `SceneContext` entry + a new Edit-mode keybind, persisting via `ScenarioSerializer.SaveToFile` (the `WinConditionPhase`/`TriggerEditorPanel` precedent).

## Boundaries & Constraints

**Always:**
- **Only init-time-eligible attributes are selectable.** The UI checklist is built *from* `PersistableAttributes.Eligible`, so a creator can never select a mid-game attribute through the editor — "only init-time-eligible attributes may be selected" is satisfied by construction. The validator is the fail-closed backstop for hand-edited scenario JSON.
- **The catalog is a closed, evidence-backed C# set** (`PersistableAttributes`, Godot-free, deterministic, Tier-1-testable), mirroring `HeroLevelingPresets`/`UnitCompositionPresets`. Today its `Eligible` entries are exactly the concrete per-instance persistable fields that exist: `hero.level` and `hero.xp` (both `HeroStore` init state loaded by 3.9). `AttributeScope { Hero, Unit, Player }` is structurally present; `Unit`/`Player` have zero eligible attributes until their backing stores land (items 3.15, meta later) — the editor renders only scopes with ≥1 eligible attribute so no empty section advertises an unbuilt system.
- **`PersistenceManifest` is purely additive authoring data on `ScenarioData`, omitted when null** (`[JsonIgnore(Condition = WhenWritingNull)]`, the `ScenarioPlayerSlot.StartCrystal` precedent). Every existing scenario has no manifest ⇒ its JSON serializes byte-identically, moving no golden. Like 3.7's `hero` block: **NO checksum/`CanonicalModelHash`/`StartStateHash` fold** — nothing consumes it at runtime this story (the fold, if ever, is 3.9's, at init-apply time). No `AlgoVersion` bump.
- **The manifest passes the D3 validate gate fail-closed.** `PersistenceManifestValidator.Validate(manifest)` accumulates located `(fieldPath, message)` errors (D-9 multi-error, mirroring `UnitDefinitionValidator`). The same rule core is invoked first-fail inside `ScenarioValidator.Validate` (returning `ValidationResult.Fail(locatedError)`), so a malformed manifest in a loaded scenario is rejected at the pre-tick gate. A null manifest is Valid (persistence simply not configured).
- **Reuse the existing editor + persistence machinery, do not rebuild it.** Compose the panel from `ChimeraSwitch` (master toggle + `BindReveal`), `ChimeraListRow`/`ChimeraComponents.FieldLabel` (per-attribute checklist + scope headers), `ChimeraValidationBadge` (section-level located badge for hand-edit errors), and `AttachFieldTip` for tooltips. Mount as an `ISetupPhase` cloning `UnitCardPhase`/`WinConditionPhase`; hold `_ctx.Scenario`; persist with `ScenarioSerializer.SaveToFile(_ctx.Scenario, ProjectSettings.GlobalizePath(_ctx.Scene.ScenarioPath))`; hide in Play via `GameState.ModeChanged`.
- **The disable toggle is explicit.** `manifest.Enabled` (JSON `enabled`) governs whether Story 3.9's picker is available; `ScenarioData.PersistenceManifest == null` means "not configured" (the default for all existing scenarios). Toggling the master switch off sets `Enabled=false` and greys the checklist while retaining the selection; the picker-availability semantics belong to 3.9.
- Every new control carries a hover-AND-keyboard-focus tooltip (`AttachFieldTip`, UX-DR53/NFR-2). Determinism/layer rules hold: `PersistenceManifest`/`PersistableAttributes`/`PersistenceManifestValidator` are Godot-free (`src/Core/Definitions/`); the panel/phase are presentation (`src/CreationSuite/`, `src/Core/Bootstrap/Phases/`).

**Block If:**
- (none — the intent, the 3.7/3.2 persistence-chain contract, and the authoring-only precedent fully determine the approach.)

**Never:**
- Never build the load/apply rail — `LocalProfileSource`, the hero-picker Save/Load UI, minting `HeroId`s, applying a profile as deterministic init state, or folding anything into `StartStateHash`. That is Story 3.9.
- Never mint a `Validated<PersistenceManifest>` (breaches the `ScenarioValidator`-only sole-minter allow-list guarded by `ValidatedSoleMinterTest`); mirror `UnitDefinitionValidator`'s plain result struct instead.
- Never fold the manifest into `SimChecksum`/`CanonicalModelHash`/`StartStateHash` or add a per-entity SoA array for it this story (no runtime consumer → no fold; keeps the goldens + stamps byte-identical).
- Never invent unit/player attributes that have no backing state today, and never hardcode a persistable attribute in a path a creator can't reach — the catalog IS the reachable, data-defined vocabulary.
- Never require an enabled manifest to select ≥1 attribute (enabled-with-zero is valid — an empty profile shape); only unknown/ineligible/duplicate keys are rejected.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Open + enable | Editor on a scenario with heroes; flip master switch on | `PersistenceManifest` instantiated (`Enabled=true`), scope-grouped eligible-attribute checklist revealed | No error |
| Select attributes | Check `hero.level` and `hero.xp` | Both keys added to `manifest.Attributes`; `DeriveProfileShape()` yields 2 ordered slots; Save writes a `persistence_manifest` block on the scenario JSON | No error |
| Disable persistence | Flip master switch off | `Enabled=false`; checklist greyed/hidden; selection retained; scenario validates clean | No error |
| Valid manifest save | `enabled:true`, attributes ⊆ eligible catalog | `ManifestValidationResult.Ok`; scenario round-trips identically; `ScenarioValidator.Validate` passes | No error |
| Unknown attribute (hand-edited JSON) | `attributes:["hero.bogus"]` | Located error keyed `attributes.hero.bogus` ("unknown attribute"); section badge + status; Save blocked; `ScenarioValidator.Validate` fails | Reject (fail-closed) |
| Mid-game attribute (hand-edited JSON) | `attributes:["hero.current_hp"]` (a known-ineligible key) | Located error keyed `attributes.hero.current_hp` ("mid-game-only state cannot be persisted"); Save blocked; gate fails | Reject (fail-closed) |
| Duplicate attribute | `attributes:["hero.level","hero.level"]` | Located error keyed `attributes.hero.level` ("selected more than once"); Save blocked | Reject |
| Null manifest (every existing scenario) | `persistence_manifest` absent | Manifest null; validators return Valid; JSON serializes byte-identically; no golden/hash moves | No error |
| No manifest → save round-trip | Load a shipped scenario, save unchanged | `persistence_manifest` still absent; file byte-identical (omit-when-null) | No error |

## Design Notes

- **D-1 — The catalog is the reachable, data-defined vocabulary; hero-only today is evidence, not omission.** The only concrete per-instance persistable state that exists is `HeroStore.Level`/`Xp` (`HeroStore.cs:78-80`), explicitly earmarked "init state loaded by 3.9." Ability-unlock and items are named in 3.2/3.7 docs but have no backing store (3.13/3.15), and no player/faction profile object exists at all (only mid-match `ResourceStore` economy). So `Eligible` = `{hero.level, hero.xp}` is the honest, complete init-eligible surface. `AttributeScope { Hero, Unit, Player }` keeps the mechanism scope-general (the story's "hero/unit/player attributes") while the editor renders only populated scopes — no empty section advertising an unbuilt system.
- **D-2 — No fold (mirrors 3.7→3.13).** The manifest is unread at runtime this story, so it moves no golden and folds into no hash. `ScenarioData` gains a nullable omit-when-null field (the `StartCrystal` precedent, `ScenarioData.cs:36-45`), `CanonicalModelHash` (`AlgoVersion=3`) and `StartStateHash` (`AlgoVersion=1`) do not walk it, and `SimChecksum` is untouched. The apply-time fold is Story 3.9's.
- **D-3 — Two gates, one rule core.** `PersistenceManifestValidator` is the authoring gate (multi-error located badges, mirroring `UnitDefinitionValidator`, NO `Validated<T>` mint). The *same* validator is called first-fail inside `ScenarioValidator.Validate` so the manifest genuinely "passes the D3 gate" and a hand-edited/cheat scenario is rejected pre-tick — without duplicating rules or breaching the `ScenarioValidator`-only sole-minter allow-list.
- **D-4 — Fail-closed only reachable by hand-edit is still required.** The checklist offers only eligible attributes, so unknown/mid-game keys can enter only by editing the scenario JSON directly. The validator (and the shared `ScenarioValidator` hook) is precisely the fail-closed backstop AR-39 demands; the section-level badge locates it (there is no per-key row for a key the catalog doesn't know).
- **D-5 — No Simple/Advanced for a flat checklist.** Story 3.8's ACs cover FR-7a/AR-12/AR-39 and deliberately omit UX-DR54/FR-6 (unlike 3.7). The manifest surface is a short attribute checklist + one toggle — there is no complexity gradient to disclose, so a Simple/Advanced segment would be vacuous; the "advanced/raw" path for a scenario is editing its JSON directly, which the fail-closed validator guards. Tooltips (UX-DR53) still apply to every control.
- **Example — authored manifest block + a hand-edit violation:**
  ```json
  "persistence_manifest": { "enabled": true, "attributes": ["hero.level", "hero.xp"] }
  ```
  `"attributes":["hero.current_hp"]` → located `attributes.hero.current_hp` "mid-game-only state cannot be persisted"; `"attributes":["hero.bogus"]` → located `attributes.hero.bogus` "unknown attribute"; both block Save and fail `ScenarioValidator.Validate`.
