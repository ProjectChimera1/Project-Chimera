## Intent

**Problem:** Story 4.8 added `ResearchDefinition`'s content model (`FactionDefinition.Research`, `BuildingDefinition.AvailableResearch`, import-time validation) but nothing runs it — a creator can author a research ladder but no order can ever start, progress, complete, or cancel it, and no unit ever receives its stat delta.

**Approach:** Add a faction-scoped `ResearchStore` (new SoA, mirrors `ResourceStore`'s per-faction-array shape) and a new `ResearchSystem : ISimSystem` (mirrors `BuildingSystem`) that: starts/cancels a research order through two new `UnitCommand` values riding the existing `OrderApplier`/exec-tick-spend path (the same shared command→world step Train/ReviveHero/BuyItem use); ticks the active order down each sim tick; on completion applies a permanent, cumulative `Modifier` (via the existing Epic 2 `ModifierStore`) to every currently alive faction unit AND wires `EntityWorld.OnUnitDefinitionApplied` (the same hook the self-passive installer uses) so every future spawn of that faction also picks it up.

## Boundaries & Constraints

**Always:**
- Research is faction-scoped, ONE order in progress per faction at a time (no per-building queue — `ResearchStore` is a new per-faction array, indices 0-4 mirroring `BuildingSystem._factions`/`ResourceStore`'s Faction-indexed arrays; there is no existing faction-scoped in-progress-order store to reuse).
- Start/Cancel are new `UnitCommand` values (`StartResearch`, `CancelResearch`, appended after `BuyItem=18` → `19`/`20`; enum stays `<= 0x3F`). WIRE: `UnitId` = the building the order is issued at (anti-cheat ownership, mirrors Train/SetRally/ReviveHero/BuyItem); `TargetX` (Start) = the chosen research's index into `FactionDefinition.Research` (mirrors Train's `chosenUnitIndex` semantics — a global list index, not a building-local one); `TargetX` (Cancel) is unused/reserved. Both dispatch in `OrderApplier.Apply` BEFORE the entity-ownership guard, exactly where Train/SetRally/ReviveHero/BuyItem dispatch.
- Completion is NEVER player-issued — it is detected per-tick by `ResearchSystem.Tick`, exactly like `BuildingSystem.TickProduction` detects training completion.
- Exec-tick spend only: `TrainUnitCommand`'s documented contract ("the deterministic spend happens HERE, at exec-tick, exactly once — never at UI click-time") applies identically to `StartResearchCommand`.
- Start gates, in order, spending nothing on any failure: (1) building alive + owned by the caller's faction — failure is SILENT (mirrors `ReviveHeroCommand`'s building-ownership guard, `BuildingSystem.cs:453`'s documented "crafted/anti-cheat orders — no feedback, no position leak"); (2) the building's `BuildingDefinition.AvailableResearch` contains the target research's `Id`; (3) the faction has no research already in progress; (4) the next level index (`ResearchStore`'s per-faction-per-research completed-level count) is `< def.Levels.Count` (not already maxed); (5) `ResearchDefinition.Prerequisites` are met — for each id, if it resolves via `FactionDefinition.IndexOfResearch` treat it as a research prerequisite (that faction's completed-level count for it must be `> 0`), otherwise treat it as a building prerequisite via `TechTreeChecker.AreMet(buildings, faction, new[]{id})` (mirrors 4.8's "resolves against the UNION of building ids and research ids"; research-id resolution checked first since `IndexOfResearch` is the more specific match); (6) `resources.CanAfford(faction, level.Cost)` (the resolved next level's cost map, `ResourceStore.CanAfford`/`Spend`'s existing `Dictionary<string,int>` overload — no new resource-store surface needed). Gates (2)-(6) each push `CombatEventType.OrderDenied` at the building's position on failure (mirrors `ReviveHeroCommand`'s affordability-guard convention, `BuildingSystem.cs:476-484`, extended here to research's other legitimate-but-rejected cases — none of them leak faction-private state the way a bare ownership mismatch would).
- On a passing Start: `resources.Spend(faction, level.Cost)`, then set the faction's in-progress state (research index, remaining ticks = `level.TimeTicks` as a plain `int` countdown — `TimeTicks` is already authored in sim ticks, not seconds, so no `Fixed` conversion applies here; decrement by 1 per `Tick` call, NOT by `dt`, exactly matching the unit the content model authored).
- On Cancel: a no-op (false, no event) if the faction has no research in progress; the named building need only be owned by the faction (cancel targets that faction's single active order regardless of which building the command names — research state is faction-wide, mirroring how any owned building can read a faction's shared `ResourceStore` balance). Refund = `CancelRefundFraction × currentLevelCost`, computed in `Fixed` (`Fixed.FromFloat(def.CancelRefundFraction)` × `Fixed.FromInt(costAmount)`, truncated via `.ToInt()` per resource key — the established authored-float→Fixed-at-use-time boundary, e.g. `BuildingSystem.cs:377`'s `Fixed.FromFloat(trainTime)` at order-start), applied via `resources.Add(faction, refundMap)` (`ResourceStore.cs:199`'s existing best-effort-restitution idiom). Clears the in-progress state.
- On completion (remaining ticks reaches 0): increment that faction+research's completed-level count; accumulate this level's `ResearchModifierDelta` into a running per-faction-per-research cumulative `Fixed` delta (four fields, mirroring `Modifier`'s four additive stat fields) — quantized via `Fixed.FromFloat` at THIS point (the single load-boundary quantization this story owns; the values are already range-validated in `[-32768, 32768)` by 4.8's `ResearchValidator`, so no second guard is needed, just the conversion); build a permanent `Modifier` (`DurationTicks: -1`, `StackRule.Refresh`, `MaxStacks: 1`, a deterministic id derived from the research's index — offset-based, mirroring `ItemSystem.ItemModifierId`/`HeroXpSystem.HeroGrowthModifierId`'s scheme, never colliding with those ranges) carrying the updated cumulative deltas; apply it to every currently alive unit of that faction (`for (int id = 0; id < world.HighWaterMark; id++)`, guarded by `world.Flags[id] & EntityFlags.Alive` and `world.FactionOf[id] == faction`, mirroring `SupplySystem.Tick`'s loop) via `Modifiers.Apply(id, mod, casterId: id, casterFaction: faction)`; push `CombatEventType.ResearchComplete` (new, appended after `ItemDropped`) at the position stored when the order started; clear the in-progress state (idle — a subsequent Start begins the NEXT level with that level's own cost/time).
- Future-spawn catch-up: wire `World.OnUnitDefinitionApplied += id => researchSys.ApplyCompletedResearch(World, id)` once, at `SimulationHost` construction (mirrors `World.OnUnitDefinitionApplied += id => abilitySys.InstallSelfPassive(World, id)` at `SimulationHost.cs:161`). `ApplyCompletedResearch` reads the spawned unit's faction, and for every research with `completedLevels > 0` re-applies that research's stored cumulative `Modifier` to ONLY the newly spawned unit (id) — this is the only hook that fires for every future spawn regardless of spawn path (training, scenario placement, hero respawn, editor restore/placement).
- `ResearchStore` is Struct-of-Arrays, `int`/`Fixed`-only, per-faction (indices 0-4) then per-research (`FactionDefinition.Research` list order) — shaped so 4.10 can fold it into `SimChecksum` without a redesign, even though this story does NOT wire that fold.
- New `ISimSystem` insertion: `ResearchSystem` is an Economy-tier system (spends resources, times an order — structurally parallel to `BuildingSystem`'s production timer) — register it immediately after `BuildingSystem` in `SimulationHost`'s system array (new index 1, shifting `GatheringSystem` and everything after down by one), and update `SystemOrderTest.ExpectedOrder` (14→15 entries) + its doc comment + the `Systems_AreTheFourteenCanonicalSystems_InExactOrder` test name/count in the SAME change (the registration order IS the determinism contract; that test fails loudly on any silent drift).

**Block If:** None — no decision here requires human input.

**Never:**
- No `SimChecksum` fold, no `AlgoVersion` bump, no golden re-baseline (Story 4.10, sequenced immediately after this one).
- No command-card UI, no research authoring editor panel, no progress-indicator widget (Story 4.11). This story's order path must be fully reachable and testable WITHOUT touching `CommandCardSystem.cs` — direct calls to `ResearchSystem.StartResearchCommand`/`CancelResearchCommand` and to `OrderApplier.Apply` with the new `UnitCommand` values are the test surface.
- No per-level modifier slot — ONE cumulative modifier slot per `ResearchDefinition` (per 4.8's Design Notes), never `StackRule.Stack`-ed per level.
- No multi-concurrent research per faction (single in-progress slot) — do not build a per-building research queue.
- Don't touch `ResearchValidator`/`ResearchDefinition`/`FactionDefinition.GetResearch`/`BuildingDefinition.AvailableResearch` (4.8, already done) beyond reading them.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy path start | Owned building lists the research in `AvailableResearch`; faction idle, affordable, prereqs met | Order queued: resources spent for level 0's cost, faction's remaining ticks = level 0's `TimeTicks` | No error |
| Happy path complete | An in-progress order's remaining ticks reaches 0 | Completed-level count +1; a permanent cumulative `Modifier` applied to every currently alive faction unit; `ResearchComplete` pushed; faction returns to idle | No error |
| Future-spawn catch-up | A faction has a completed research; a NEW unit of that faction spawns afterward (any spawn path) | The new unit receives the same cumulative modifier at spawn, via `OnUnitDefinitionApplied` | No error |
| Cancel with refund | An order is in progress; Cancel issued from an owned building | Order cleared; `CancelRefundFraction × currentLevelCost` credited back per resource key | No error |
| Cancel when idle | No order in progress; Cancel issued | No-op: no refund, no event, no state change | Silent no-op |
| Start while already in progress | Faction already has an active order | `OrderDenied` at the building; nothing spent, nothing changed | Deterministic reject |
| Start at max level | `completedLevels == def.Levels.Count` for the target research | `OrderDenied`; nothing spent | Deterministic reject |
| Start with unmet prerequisites | A named `Prerequisites` building or research entry isn't satisfied | `OrderDenied`; nothing spent | Deterministic reject |
| Start not offered at this building | Target research id absent from the named building's `AvailableResearch` | `OrderDenied`; nothing spent | Deterministic reject |
| Start insufficient resources | `resources.CanAfford` fails for the next level's cost | `OrderDenied`; nothing spent (check-all-then-spend-all, never partial) | Deterministic reject |
| Start/Cancel building not owned | `buildingId`'s `FactionOf` != the issuing faction | No-op (anti-cheat), mirrors `TrainUnitCommand`/`ReviveHeroCommand` | Deterministic reject, no event (matches existing ownership-guard precedent — a crafted cross-faction id is a silent no-op, not a denial cue) |
| Repeatable re-research | A research completes level N; Start is issued again for the same research | Begins level N+1 using level N+1's OWN cost/time (not level N's) | No error |

- `SimulationHost.cs` -- construct + register `ResearchSystem`, wire the `OnUnitDefinitionApplied` catch-up subscriber -- makes the system live in every host.
- `SystemOrderTest.cs` -- update `ExpectedOrder` + doc/test name for the new 15-system order -- keeps the determinism-contract test truthful.
- `ResearchSystemTests.cs` (new) -- cover every I/O-matrix row, plus a repeatable-ladder test (complete level 0, then start+complete level 1 with its own cost/time) and a future-spawn-catch-up test (spawn a unit AFTER a research completes; assert it carries the modifier).

**Acceptance Criteria:**
- Given a faction with an owned building offering an authored research and sufficient resources, when `StartResearch` is issued at that building, then the level's cost is spent exactly once (exec-tick, never at issue-time) and the faction's order begins counting down from that level's `TimeTicks`.
- Given an in-progress order whose remaining ticks reaches zero, when `ResearchSystem.Tick` next runs, then every currently alive unit of that faction receives the research's cumulative permanent stat modifier, a `ResearchComplete` event is pushed, and the faction's next `StartResearch` for that id begins the NEXT level using that level's own cost/time.
- Given a faction with a completed research, when a new unit of that faction spawns via ANY spawn path (training, scenario placement, hero respawn, editor restore/placement), then that unit also carries the cumulative modifier — without re-triggering research completion or re-spending resources.
- Given an in-progress order, when `CancelResearch` is issued from any owned building, then the order is cleared and `CancelRefundFraction × currentLevelCost` is credited back per resource key; issuing `CancelResearch` with no order in progress is a silent no-op.
- Given any Start guard failure (already in progress, max level, unmet prerequisite, not offered at the named building, unaffordable, or building not owned), when `StartResearch` is issued, then nothing is spent, no state changes, and (where the building IS owned) an `OrderDenied` event is pushed at the building's position.

## Design Notes

**Why a single faction-wide in-progress slot, not a per-building queue:** the investigation found no existing faction-scoped in-progress-order store — every prior timed order (construction, training) is building-scoped. Given research's own content model is faction-wide (one `FactionDefinition.Research` list, one permanent effect on the whole faction) and this story was already split three ways to fit a session budget, a single active order per faction is the minimal design that satisfies the AC ("start/complete/cancel") without inventing new per-building state that 4.10's fold would also have to cover. A creator wanting parallel research lines is a future extension, not this story's scope.

**Modifier id scheme:** mirrors `ItemSystem.ItemModifierId(itemRef) => ItemModifierIdBase + itemRef` (`Combat/ItemSystem.cs:73`) and `HeroXpSystem.HeroGrowthModifierId = 0x3133_0000` (`Combat/HeroXpSystem.cs:39`, the two ASCII-digit-byte convention for story-numbered constants). A `ResearchModifierId(int researchIndex) => ResearchModifierIdBase + researchIndex` keeps one stable, non-colliding id per (faction-scoped) research entry across its whole cumulative lifetime — `StackRule.Refresh` re-applies mean each completion updates the SAME slot's deltas rather than stacking a new one, so `EffectCaps.MaxModifiersPerEntity = 8` (`Effects/EffectCaps.cs:70`) is never at risk from research alone.

**Why `TimeTicks` is a raw `int` countdown, not `Fixed` seconds:** unlike `BuildingStore.ProductionTimer` (`Fixed` seconds, decremented by `dt`), 4.8 deliberately authored `ResearchLevel.TimeTicks` as sim ticks (an `int`), so `ResearchStore.RemainingTicks` decrements by exactly 1 per `ResearchSystem.Tick` call — the authored unit IS the tick, no `Fixed`/`dt` conversion belongs here. The one `Fixed` quantization this story owns is the `ResearchModifierDelta` floats, converted once per completed level (already range-validated by 4.8, so `Fixed.FromFloat` cannot overflow).
