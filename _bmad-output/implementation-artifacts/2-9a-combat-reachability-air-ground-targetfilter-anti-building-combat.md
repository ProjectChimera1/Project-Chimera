## Story

As a player,
I want units to honor anti-air / anti-ground target filters and to be able to attack enemy buildings,
So that the showcase factions' combat resolves against the right targets and armies can destroy structures.

## Why this matters (source-verified)

Today `CombatSystem` picks targets **purely by nearest-enemy**: the only filter in the acquire loop is `if (world.FactionOf[j] == myFaction) continue;` (`SpatialHash.cs:107`, mirrored at `:139`). There is **no air/ground distinction and no unit/building distinction**, and damage resolves **only against `EntityWorld`** (`DamageResolver.Apply` is hard-bound to `world.Health[t]` / `world.EffectiveArmor[t]` / `world.Destroy(t)`). The design doc flags both gaps as **needs-code**:

- Anti-air: *"CombatSystem ignores Air/Ground entirely — anyone in range is a valid target. True anti-air discrimination (and flyer-only / can't-hit-air rules) needs D1 TargetFilter plus a CombatSystem rewire to honor it."* (`fma-faction-design.md:171`)
- Anti-building: *"Projectile/splash code only iterates EntityWorld units, not BuildingStore. Both sieges' anti-structure role does not function today … Needs ApplyHit/ApplySplash to target buildings."* (`fma-faction-design.md:112,124,173`) — **Siege units are the intended anti-structure counter**; buildings are currently **indestructible in-match** (the only `BuildingStore.Destroy` caller is the editor delete tool, `EntityPlacer.cs:1029`).

Story 2.8 made the full rosters (incl. the Air units `griffin`/`wyvern`) trainable. 2.9a makes their combat **correct**: air units get properly countered, and armies can finally raze an enemy base. This unblocks **2.10** (showcase signature mechanics) and **2.9b** (worker-cast / crystal cost), both of which depend on 2.9a.

_Covers: FR-11, FR-12, AR-8, NFR-4. Depends on: 2.4 (ability/command-card spine — done), 2.8 (Air building + `OrderApplier` `BuildingSystem?` threading — done)._

## Acceptance Criteria

### AC1 — Air/ground target filter in auto-acquire (epic AC1, verbatim + made testable)

**Given** a unit whose attackable-domain set excludes a domain, and both a matching and a non-matching enemy in range **When** `CombatSystem` selects a target **Then** it engages **only** an enemy whose domain the unit may attack — an anti-air-only unit (`attack_domains: ["Air"]`) engages only the flying enemy (`CategoryOf == Air`) and a ground-only unit engages only the ground enemy — **And** target selection remains deterministic and **ascending-id stable** (the filter only prunes candidates before the existing strict-nearest compare; ties still resolve to the lowest-id candidate).

- **AC1.1** The domain filter is applied in **both** acquire paths — `SpatialHash.FindNearestEnemy` (in-range, `:107`) **and** `FindNearestEnemyGlobal` (idle chase-to-contact, `:139`) — so an anti-air unit with no valid air target does **not** march toward a ground enemy it can never damage.
- **AC1.2** "Is the candidate flying?" is read from **`EntityWorld.CategoryOf[j]`** (`UnitCategory.Air == 4`), never from `armor_type` (the two shipped air units have **different** armor: `griffin`=Light, `wyvern`=Medium — armor cannot identify air).
- **AC1.3** The default (unauthored) attackable-domain set is **All** — every existing unit attacks every domain exactly as today. No shipping faction JSON is edited; the AC1 restricted-unit case is exercised with a **synthetic test unit**, so no golden moves (see AC3).
- **AC1.4** A unit's own domain (`CategoryOf`) does **not** restrict what it can attack; the new `attack_domains` field is a distinct **attacker-capability** axis. (An Air unit with default `All` still hits ground; an `["Air"]` ground unit hits only fliers.)

### AC2 — Anti-building combat, explicit-order-only (epic AC2, verbatim + made testable)

**Given** a combat unit **ordered** to attack an enemy building **When** it is in range **Then** it deals damage to that building in `BuildingStore` via the **DamageMatrix** (`amount × DamageTable.Get(attackerDamageType, ArmorType.Fortified)`, floored at 0) and can **destroy** it (`Health ≤ 0 → BuildingStore.Destroy`) **And friendly buildings are never targeted** (`buildings.FactionOf[b] == attackerFaction` is rejected at both order-apply and combat-resolve time).

- **AC2.1** Anti-building is **explicit-order-only**: idle/auto-acquire never targets buildings (buildings are not in the combat `SpatialHash`; nothing is added to it). This is a determinism requirement — see AC3.
- **AC2.2** Building damage uses the **matrix path** (not `DirectHpDelta`): a Siege attacker (Siege vs Fortified = 1.5×) razes structures fast; a Pierce attacker (Pierce vs Fortified = 0.25×) barely dents them — matching the intended counter design.
- **AC2.3** An out-of-range attack-building order makes the unit **chase** to the building's `Position` (Fixed center point) and then fire when in `AttackRange`; on the building's death the attacker reverts to Idle. Cooldown gating (`AttackCooldown`/`AttackSpeed`) is honored exactly as unit-vs-unit.
- **AC2.4** A unit whose `attack_domains` excludes **Structure** cannot be ordered to attack a building (the order is rejected / no-ops). Default `All` includes Structure, so every existing combat unit can attack buildings when ordered.
- **AC2.5** Ordering an attack on a building **under construction** is allowed (standard RTS; `IsUnderConstruction` is not a shield). A **Neutral** building is a valid target when explicitly ordered (unit combat already treats Neutral as hostile).

### AC3 — Determinism & zero regression (explicit; prevents "completion lies")

**Given** the change set **When** the Tier-1 golden gate runs **Then** all **10** golden checksums are **byte-identical**, `SimChecksum.AlgoVersion` stays **8**, `CanonicalModelHash` AlgoVersion stays **2**, the known-state pin `0x983D39AE` is unchanged, and `VersionStampConsistencyTests` (8/2/1/2 + "0.1") passes. **And** `ApplyUnitDefinitionGuardTest` passes with the new `AttackDomainOf` field asserted. **No fold, no AlgoVersion bump, no golden re-record.**

- **AC3.1** The new `AttackDomainOf` per-unit field is **authored-immutable → NOT folded** (the `DamageTypeOf`/`ArmorTypeOf`/`CategoryOf` posture — all combat-read authored fields, none folded; a divergent authored choice is caught transitively when the differing target's already-folded `Position`/`Health` move).
- **AC3.2** Anti-building damage writes `buildings.Health` / `buildings.Alive`, which are **already folded** (`SimChecksum.cs:185-186`) — **no new fold**. No new folded SoA field is introduced for the building target (the building id rides the already-folded `CommandTarget` under `CommandState == AttackBuilding`).
- **AC3.3** No golden moves: **no golden scenario spawns an Air-category unit** (only `"Worker"` appears, in `GoldenApplierScenario`) so the default-`All` filter is inert everywhere; and the 3 goldens that place buildings (`golden-scenario`, `golden-multifaction`, `ai-active`) **never issue an attack-building order**, so explicit-order-only leaves them untouched.
- **AC3.4** New coverage lands as **new** golden(s) — a `combat-air-ground` filter golden and an `anti-building` destruction golden — never by editing the existing 10.

### AC4 — MP-deterministic anti-building (the order rides the lockstep wire)

**Given** two peers (or a live match and its `.chmr` replay) **When** a player orders a unit to attack an enemy building **Then** the action rides the deterministic command stream as a new `UnitCommand.AttackBuilding = 12` through the **shared `OrderApplier.Apply`**, applied identically on every peer and in replay, with **no wire/replay/version bump** (rides the existing 11-byte `UnitOrder`; `ReplayRecorder.VERSION`/`PROTOCOL_VERSION` unchanged — the `Train`/`CastAbility` precedent). **And** all **three** apply sites stay one switch (`LockstepManager` / `ReplayPlayer` / offline `SelectionSystem`) — the offline site is wired to pass the `BuildingSystem?` param so offline attack-building actually damages (AR-17 structural parity). **And** the attacker-ownership guard (own-unit-only) is preserved and the friendly-building guard is enforced in the apply path.

### AC5 — UX (right-click an enemy building issues the attack)

**Given** a selection of the player's combat units **When** the player right-clicks an enemy building **Then** an attack-building order is issued (the right-click dispatch resolves an enemy **building** pick between the existing enemy-**unit** pick and the Move fallback), and the units move to and destroy it. `/godot-verify` confirms the picker, the chase, matrix damage, destruction, and the friendly-building no-op in-engine.

## Decisions

**Baked in (deterministic-rule / minimal-slice calls — applied, not re-asked):**

1. **Anti-building is EXPLICIT-ORDER-ONLY (not auto-acquire).** Buildings are not in the combat `SpatialHash` (entity-only buffers), so idle units cannot auto-target them without adding building candidates to the hash — which would change `golden-scenario`/`golden-multifaction`/`ai-active` (their surviving enemy units would march on the nearby enemy buildings) and force a 10-golden re-record. Explicit-order-only keeps every golden byte-identical **and** matches the epic wording ("a combat unit **ORDERED** to attack an enemy building"). Auto-acquire of buildings (arrived AttackMove waves picking a base) is a deliberate **later** enhancement (see `deferred-work.md` item 7), out of scope here.
2. **`AttackDomain` default = All.** A new authored-immutable field defaulting to `All` means existing faction JSON needs **zero** edits, `CombatSystem` behavior is unchanged, and all 10 goldens stay byte-identical. Author opt-in **restriction** only. Set in `EntityWorld.Create()` (recycle-slot safety) and written via `ApplyUnitDefinition`.
3. **No fold, `AlgoVersion` stays 8.** `AttackDomainOf` is authored-immutable (`DamageTypeOf`/`ArmorTypeOf`/`CategoryOf` posture → not folded); building `Health`/`Alive` are already folded → anti-building adds no fold; the persistent building target reuses the already-folded `CommandTarget` (no new folded SoA). ([[chimera-checksum-fold-timing-rule]])
4. **`UnitCommand.AttackBuilding = 12`** (append after `Train=11`; values 0–11 frozen for replay). Pack the **attacker entity id in `UnitId`** (so the existing entity-ownership guard at `NetworkCommand.cs:135-137` validates it for free) and the **building id in `TargetX`** as a raw int (`Fixed.FromRaw` at issue, read as `o.TargetX` — never `.ToFloat()`). The case goes **inside** the switch **after** the ownership guard (unlike `Train`, which names a building in `UnitId` and is handled before the guard). Store the target as `CommandState[id] = AttackBuilding` + `CommandTarget[id] = buildingId` — `CommandState` disambiguates which store `CommandTarget` indexes (mirrors how `AttackTarget`/`Follow` already share `CommandTarget`). **Do NOT reuse `AttackTarget=6`**: it reads `CommandTarget` as an **entity** id (`world.IsAlive`/`FactionOf`), and a building id there mis-indexes the entity SoA.
5. **`AttackDomain` includes a `Structure` bit; the ordered attack-building is gated on it.** Default `All` (Ground|Air|Structure) so every existing combat unit can be ordered to attack buildings; a creator authoring `attack_domains: ["Air"]` gets an AA-only unit that also cannot hit buildings (AC2.4).
6. **AC1 demo uses a synthetic test unit**, not a shipping-roster edit — editing a fielded unit could move a golden; a synthetic `["Air"]` unit in a dedicated test scenario moves nothing. (There is no dedicated AA unit in either roster today; the design doc designates the `archer`/Pierce Marksman as the anti-air *finisher* but nothing in data expresses targeting — a fielded AA unit is a **content** decision for later, kept off every golden scenario.)

- **D-1 (SCOPE — ability-side reserved bits): DEFER — 2.9a ships the COMBAT ACs only.** The reserved `Effects.TargetFilter.Air/Ground/Structure` bits (stamped "reserved for Story 2.9a") are the **ability-side** `SearchArea` domain filter (evaluated by `TargetMatcher`) — a **distinct mechanism** from AC1/AC2 (combat auto-acquire + building damage). Neither AC requires touching them. Unlocking them pulls in the ability-authoring blast radius (lift the fail-closed reject at `EffectNodeJsonConverter.cs:246`, add to `DraftVocabulary.Filters` / `AbilityDraft.cs:53`, editor exposure, and the guarded `FlagCombinationVocabularyTests` / `ReservedTargetFilterBit_IsLocatedReject` tests). **Recommended: defer** (scope discipline — the project's explicit anti-pattern is "ship everything at once"); Task 11 updates the reserved-bit comment to point at the follow-on so it isn't left lying. If Alec wants the deferral fully closed now, it becomes an explicit added task (evaluate the bits in `TargetMatcher` via the shared `CategoryOf → domain` classifier + lift the reject + vocabulary + tests).
- **D-2 (reuse): NEW Core `AttackDomain` flags enum — do NOT reuse `Effects.TargetFilter`.** The `Effects` Air/Ground/Structure bits are **actively rejected** on the ability path and absent from the composer vocabulary — the *same value* would be "forbidden" for abilities yet "valid" on a unit field (split-personality enum). And it is a different axis (attacker capability vs ability target predicate; the allegiance bits are meaningless on a unit's attack-capability field). Recommended: `[Flags] enum AttackDomain : byte { None=0, Ground=1<<0, Air=1<<1, Structure=1<<2, All=Ground|Air|Structure }` in `src/Core`, with a shared `CategoryOf → domain` classifier both this and any future ability-side unlock can consume. (`game-architecture.md:415` envisions one shared TargetFilter vocabulary long-term; the shared classifier is the honest reconciliation without importing the ability enum's baggage.)
- **D-3 (building armor): hardcode `ArmorType.Fortified` at the damage call.** **100%** of shipped building JSON authors `armor_type: "Fortified"`, and `BuildingStore` has no `ArmorType` field (`Create` ignores building JSON entirely today). Recommended: pass the `Fortified` constant (zero new SoA, no fold, correct for all current data). The creator-extensible upgrade — `BuildingStore.ArmorType[]` fed from `def.ParsedArmorType` at placement — is noted out-of-scope (it requires `BuildingStore.Create` to start reading the def and belongs with a larger data-driven-building arc).
- **D-4 (ranged-vs-building): resolve building damage INSTANTLY in `CombatSystem`** (both melee and ranged attackers), not via a projectile. `ProjectileStore.TargetId` is an **entity** id and `ProjectileSystem` has zero building references; carrying a building target through projectiles needs `BuildingStore` in `ProjectileSystem` (`SimulationHost.cs:128`) + a target-kind flag — more surface + risk for no AC benefit. Recommended: instant matrix damage in `TickAttackBuildingCombat`; the missing shell-flight **visual** for ranged-vs-building is deferred presentation polish (noted, not built).

### Current state — precise, source-verified

**Combat target selection (sim).** `CombatSystem.Tick` (`CombatSystem.cs:64`) rebuilds the `SpatialHash`, then scans entities **ascending-id** (`for i in 0..HighWaterMark`), skipping dead / gatherers / zero-`EffectiveAttackDamage` non-combatants (`:86-103`), and dispatches on `world.CommandState[i]` to one of 8 tick handlers. The idle/auto-acquire path `TickIdleCombat` (`:144`) validates the current target, else calls `_spatialHash.FindNearestEnemy` (in-range) then `FindNearestEnemyGlobal` (chase-to-contact). Both acquire methods filter candidates by **faction only** (`SpatialHash.cs:107` and `:139`) then pick strict-nearest (`sqrDist < bestSqrDist`, so ties → lowest-id). `TickStationaryCombat`/`TickAttackMoveCombat`/`TickPatrolCombat` reuse the same acquire calls → **the two `SpatialHash` methods are the single AC1 insertion point.**

**Damage (sim).** `TryDealDamage` (`:465`) gates on `AttackCooldown`, resets to `AttackSpeed`, then splits melee vs ranged at `MELEE_THRESHOLD = 2.5`: ranged spawns a projectile (delayed), melee calls `DamageResolver.Apply` directly, both reading `EffectiveAttackDamage`/`DamageTypeOf` (post-2.2a Effective\*). `DamageResolver.Apply` (`DamageResolver.cs:52`) is **entity-only**: `final = max(0, amount × Table.Get(type, TargetArmor) − world.EffectiveArmor[t])`, then `world.Health[t] -= final`, and on lethal pushes `UnitKilled` + `RecordKill` + `world.Destroy(t)`. It **cannot** damage a building (no `BuildingStore` awareness) — AC2 needs a parallel path sharing only the matrix formula.

**Buildings (sim).** `BuildingStore` is 14 parallel SoA arrays (`MAX_BUILDINGS = 64`), dense `0..Count-1`, **no free-list reuse** in Phase 1. It has `Alive`/`Position` (Fixed center)/`FactionOf`/`Type`/`Health`/`MaxHealth`/construction/production — **no `ArmorType`** and no `DamageType`. `Create(position, faction, type)` hardcodes HP by `BuildingType` and **ignores the JSON** (`hp`/`armor_type` are vestigial). Buildings take **zero** combat damage today; `Destroy(id)` (just `Alive[id]=false`) is called only by the editor delete tool. Buildings are **not** in the combat `SpatialHash` (entity-only buffers) — they register only with `NavObstacleManager` (presentation nav). `ArmorType.Fortified = 4` (enum comment "// Buildings") already has a fully-tuned matrix column (Normal 0.35, Pierce 0.25, Siege 1.50, Magic 0.50, Hero 1.0) — **reuse it, invent no new armor**.

**The air tag already exists.** `EntityWorld.CategoryOf` (`:246`, `UnitCategory` with `Air=4`, `Structure=5`) is the per-unit movement-domain tag, written by the single mapper `ApplyUnitDefinition` from `def.ParsedCategory`, defaulted `Melee` in `Create()`, and **not folded** (presentation-read like `MeshType`). `grep flying|IsAir|CanAttackAir|antiAir` returns **zero** — there is no other air representation, and `MovementSystem` has **no** air special-casing (air units are ground units carrying a tag). So AC1 needs exactly **one** new thing: the attacker's **capability** (`AttackDomainOf`), read against each candidate's `CategoryOf`.

**Command wire (MP).** `UnitOrder` is 11 bytes: `UnitId(ushort)` + `Command(byte)` + `TargetX(int)` + `TargetZ(int)`; `TargetX/Z` are raw `Fixed` ints. `OrderApplier.Apply` (`NetworkCommand.cs:116`) is the **single** command→world switch called verbatim by `LockstepManager`, `ReplayPlayer`, and offline `SelectionSystem` (AR-17 structural parity). `Train=11` is the "UnitId names a building" precedent — handled **before** the ownership guard. `AttackTarget=6` writes `CommandTarget[id] = o.TargetX` (an **entity** id) and is consumed by `TickAttackTargetCombat` with `world.IsAlive`/`FactionOf` — **a building id there mis-indexes the entity SoA**, which is exactly why AC2 needs a dedicated `AttackBuilding=12` (attacker in `UnitId`, so it goes *after* the guard).

### Determinism notes (no fold, `AlgoVersion` stays 8, 10 goldens byte-identical)

- **`AttackDomainOf` is NOT folded.** It is authored-immutable and read in-sim by target selection — exactly like `DamageTypeOf`, `ArmorTypeOf`, and `CategoryOf`, **all** of which are combat-read authored fields and **none** of which are folded (`SimChecksum` folds `Effective*` outcomes, not authored inputs). A divergent authored domain choice changes which target is hit → the affected entity's already-folded `Position`/`Health` move → caught transitively. This follows [[chimera-checksum-fold-timing-rule]] (fold only when a field first becomes **mutable** mid-match). *(Noted tension: `CollisionRadius`/`SeparationPriorityOf` were folded at v5 despite being authored-immutable, on a "read every tick" rationale. The dominant and most-analogous precedent — `DamageTypeOf`/`ArmorTypeOf`/`CategoryOf`, the sibling combat-targeting authored fields — is **not** folded; follow them, keep v8, ratified in D-3/AC3.)*
- **Anti-building adds no fold.** `buildings.Health`/`Alive`/`ConstructionTimer` are already folded (`SimChecksum.cs:185-188`) — a peer divergence in building damage moves the **directly**-hashed `buildings.Health`. The persistent building target rides the already-folded `CommandTarget` under `CommandState = AttackBuilding`; **no new folded SoA field** is introduced.
